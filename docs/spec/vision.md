# Sumire — プロダクトビジョン

本書は Sumire の哲学・差別化軸・対象ユーザーを定める恒久文書。実装の正は `.kiro/steering/` と他の `docs/spec/`(`architecture.md`, `ux.md`, `roadmap.md`)に置き、本書はそれらの上位にある「なぜこのプロダクトを作るのか」に閉じる。

## 名称

**Sumire**(すみれ)

由来は二重の意味:

- **墨入れ**: 墨を入れる(=書く)道具。執筆の伴侶であることを示す。
- **菫**: 早春に咲く小さな花。出しゃばらず書き手のそばに静かに咲く、というプロダクト思想と重なる。

## 一行で言うと

> ローカル LLM とクラウド AI を切り替えながら、日本語 Web 小説を執筆できるデスクトップアプリ。

## 目的

自分の手で日本語 Web 小説を書きたい人のための、AI を「優秀な共著者」として使える執筆環境を提供する。

AI に全部書かせるのではなく、書き手の手元で続きを提案し、Tab キー一つで採用できる Copilot 風の体験を、小説執筆向けに最適化する。

## ターゲットユーザー

- 自分で書きたい意志がある日本語 Web 小説の書き手。
- 既存の AI 小説生成サービス(全自動型・SaaS 型)では物足りない、または手元で動かしたい層。
- ローカル LLM・クラウド AI を試行錯誤しながら使い分けたい層。

## 設計哲学

恒久的に守る判断軸。詳細な技術選定は `architecture.md` を参照。

- **AI プロバイダはアダプタパターンで差し替え可能**に設計する。OpenAI 互換を共通インターフェースとし、Claude/Gemini など非互換 API は別アダプタで吸収する。特定ベンダーへの依存を避ける。
- **文脈管理(プロンプト構築)ロジックを独立モジュール**に切る。コンテキスト長制約のもとで何を含め何を省くかの戦略をここに集約し、プロバイダ非依存に保つ。
- **設定・本文・履歴は人間可読な形式**(Markdown + JSON)で保存し、ベンダーロックインを避ける。書き手が Sumire を使わなくなっても、自分のデータを自分のものとして持ち続けられる。
- **推論は独立プロセス**に切り出し、アプリ本体とは HTTP/WebSocket で通信する。アプリ自体は推論ロジックを持たない。推論サーバーは書き手が選べる(text-generation-webui / Ollama / LM Studio 等)。書き手が自分で起動した推論サーバーにつなぐプロバイダのほかに、Sumire が推論サーバー(llama.cpp の `llama-server`)を子プロセスとして自分で起動・停止するプロバイダもある(2026-11-12、`llama-server-provider` spec)。その場合も推論は別プロセスのままで、HTTP で話す。推論エンジンをアプリのプロセス内に組み込むことはしない(推論が落ちたときに、エディタと未保存の原稿を巻き込まないため)。管理の主体と採らなかった案は `architecture.md`「推論サーバーの管理」「llama-server プロバイダ」を参照。

## 先行類似プロダクトとの差別化

新機能を追加する際は「Sumire の差別化軸に沿うか」を基準にし、競合に追随することを目的とした機能追加は避ける。

同ジャンルには、機能面で Sumire より厚いツールが先行している。ノードグラフによるプロットの構造化、プロット間のストーリー生成補完、ショートカットでの続き生成、複数のクラウドプロバイダへの対応、画像生成との連携、縦書きプレビュー、EPUB 出力までを 1 つにまとめた、総合環境型のツールである。機能の総量では、Sumire は及ばない。

そのうえで Sumire の存在意義は「**狭い軸に特化する**」ことに置く。総合環境型のツールが「構造化 + AI 加筆コマンドの総合パッケージ」であるのに対し、Sumire は「本文を書いている流れの中で、続きをインラインで提案し Tab で採用する」体験**だけ**を磨く。比較表は機能の優劣ではなく、重心の違いとして読まれたい:

| 軸 | 総合環境型のツール | Sumire |
| --- | --- | --- |
| 重心 | 構造化 + AI 加筆の総合環境 | 連載執筆中の続き提案に特化 |
| AI 続き生成の起動 | コマンド/ショートカット駆動 | 常時インライン提案 + Tab 採用 |
| 入力起点 | ノードグラフ + 本文 | 本文そのもの |
| プロバイダ抽象 | 複数のクラウドプロバイダ + ローカル | OpenAI 互換 HTTP API を共通の形にし、アダプタで拡張する。今あるのは、ローカルの OpenAI 互換、OpenAI(クラウド)、Sumire が起動する llama.cpp(`llama-server`)の 3 つ |
| メモ機能 | 汎用ノードグラフ | キャラ・世界観に特化、プロンプト自動挿入 |
| プロット支援 | ノード間のストーリー生成補完 | 提供しない(本文起点を崩さないため) |
| 想定利用シーン | 構想・整理・推敲を含む全工程 | 連載執筆の日次ワークフロー |

総合力では、Sumire は総合環境型のツールに及ばない。Sumire は「インライン Tab UX × 本文起点 × 連載日次ワークフロー」という細い軸の専用ツールに留まることで、別ジャンルとして成立させる。

### Sumire が守るべき軸

1. **Copilot 風インライン Tab 採用 UX** — 本文を書いている流れを切らずに続きを提示する。チャット型にはしない。
2. **本文起点の文脈構築** — ノードグラフのような中間表現を必須にしない。本文 + メモ(キャラ・世界観)で完結する。
3. **OpenAI 互換 API をプロバイダ抽象に** — text-generation-webui / Ollama / LM Studio などローカル推論サーバーを横断的に扱える設計を保つ。Sumire が起動する `llama-server` も、同じ OpenAI 互換の HTTP API で話す。
4. **日本語 Web 小説の連載執筆ワークフローへの最適化** — 章 = エピソード単位、毎日エディタを開いて続きを書く動線が一級市民。

## ジャンル特化の前提

日本語 Web 小説に特化して設計する。文脈管理・タイポグラフィ・章=エピソード単位の構造などはこの前提に最適化する(具体的なルール・実装方針は `architecture.md` および `ux.md` 参照)。

英語・他ジャンル対応は将来の拡張課題とする。
