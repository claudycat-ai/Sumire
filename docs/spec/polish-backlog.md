# Sumire — 磨き込みバックログ

MVP(2026-04-29 時点で M0〜M8 全完了)後に着手する、機能追加ではなく「使用感の磨き込み」項目を集めたバックログ。

## このファイルの位置づけ

- 本ファイルは**仕様**ではなく、**観察に基づく磨き込み TODO のメモ**。優先度・採否・実装時期は別途判断する。
- 機能追加は `roadmap.md` の拡張ロードマップで扱う。本ファイルは**既に動いている機能の触り心地**に閉じる。
- 触発元(competitor / dogfooding / ユーザーフィードバックなど)を各項目に記録しておくと、判断時の文脈が再現できて良い。

## 着手指針

MVP 完成直後は、磨き込みより**Sumire の差別化軸を強化する機能**(本文起点の文脈構築、Tab 採用 UX のさらなる作り込み等)を優先する。磨き込みは差別化軸の確立後にまとめて回収する方が、軸を見失わない。

ただし「**書き手として日常使用したときに頻繁に引っかかる**」項目は例外的に先行して直す。バックログ項目を直す判断は「仕様に書く価値があるか?」で線引きする — 仕様化できるなら拡張テーマ、UI の質感調整なら磨き込み。

## バックログ

### エディタ周りの触り心地

- [x] **暗黙のキャンセルでゴーストが消えず、以後そのエディタでキャンセルが効かなくなる**(触発元: thinking-output spec のタスク 3.1 のレビュー 2026-11-01、2026-11-01 完了)
  `suggestionLifecycle.ts` の `cancel()` が、`ViewPlugin.update()` の中で `view.dispatch` を呼んでいる。CodeMirror は「Calls to EditorView.update are not allowed while an update is in progress」を投げ、そのプラグインを無効にする。そのため、提案の表示中やストリーミング中に文字を入力・カーソルを移動すると、HTTP リクエストは切れるがゴーストが残る。以後そのエディタでは暗黙のキャンセルが働かない。思考中なら「思考中… N 秒」が数え続ける。M3-c(2026-04-28)からある。2026-11-01 に一時的なテストで再現した。ux.md「提案のキャンセル挙動」のとおりに動いていないバグなので、小さなバグ修正として直す。直すときは、`dispatch` を `update()` の外に出す方向で考える。
  → HTTP の切断はその場で行い、提案を消す dispatch だけをマイクロタスクで更新の後に回した。その間に別の提案が表示されていたら消さない。提案の状態そのものに「文字入力で消える」規則を持たせる案は採らなかった。消える処理が文字入力と同じトランザクションに入り、採用時だけ走るはずの中央寄せのスクロール(`suggestionScroll` の「消えた + 文書が変わった」)が、文字を打つたびに走るため。

### 採らない方針(react-doctor)

- [ ] **エラートーストの文言を OpenAI 利用時にも合うようにする**(触発元: provider-http-rust spec の調査 2026-10-22)

- [ ] **提案生成のトーストに、日本語の直書きと i18n 経由が混ざっている**(触発元: thinking-output spec の実装 2026-11-01)
  `suggestionController.ts` の既存のトースト(「推論サーバーに接続できません」「提案を取得できませんでした(応答が空です)」「メモに転記しました」など)は日本語の直書きで、thinking-output で足した思考のトースト(`toast.thinkingMaxTokens` / `toast.thinkingUnfinished`)だけが i18n を通る。en ロケールでは、英語と日本語のトーストが混ざる。既存の文言を `ja.json` / `en.json` のキーに寄せる。上の「エラートーストの文言を OpenAI 利用時にも合うようにする」と同時に扱うと、文言を 1 回で見直せる。
  2026-11-05(illustration-prompt spec)以降、接続・HTTP などのエラー文言は共有の関数 `describeProviderError` が日本語の直書きで持ち、続き生成と挿し絵の情景文の両方が使う。挿し絵の情景文のほかのトーストは i18n を通るので、en ロケールではエラーのときだけ日本語が出る。i18n に寄せるときはこの関数を直せば両方に効く。
- [x] **gpt-5 系モデルで生成が HTTP 400 になる**(触発元: provider-http-rust の手動 E2E 2026-10-22、2026-10-22 完了)
  OpenAI の Chat 経路が `max_tokens` を送っており、gpt-5 系(推論モデル)は「`max_completion_tokens` を使え」として拒否する。`temperature` / `top_p` を既定値以外にできない制約もあるはずなので、モデル系統ごとのパラメータの送り分けを含めて扱う。機能が動かない問題なので、磨き込みより優先度は高い。
  → Chat 経路は全モデルで `max_completion_tokens` を送るよう統一した。推論モデル(`gpt-N`(N ≥ 5)と `o` + 数字。前方一致で判定)には temperature / top_p を送らない。AI 設定画面では、推論モデルを選んでいるときにその旨を注記する。
  判断の理由:
  - `max_tokens` は公式に deprecated。統一すれば、モデルによって分岐させるのは temperature / top_p だけで済む。
  - 推論モデルと判定する範囲は、安全側に広く取った。誤判定しても temperature が効かないだけで、400 にはならない。
  - temperature を効かせたい場合は `extras` で上書きできる。
  - 規則の詳細と出典は `architecture.md`「OpenAI アダプタのパラメータの送り分け」に書いた。Completion 経路(`-instruct`)は `max_tokens` のまま。
- [ ] **モデルを替えてもトークン数の計測キャッシュが古いまま残る**(触発元: prompt-template spec のタスク 2.2 の実装 2026-11-04)
  ContextBuilder の計測キャッシュ(`contextBuilder.ts` の `sectionTokenCache`)は、キーが計測した文字列だけで、モデルやプロバイダを含まない。クリアする関数(`clearContextBuilderCache`)はテストからしか呼ばれていない。そのため、トークナイザの違うモデルに替えても、設定ファイルやテンプレートの文字列は前のモデルで測った値のまま予算計算に使われる。日本語のトークン消費はモデルによって 2 倍ほど違うので、コンテキスト窓を超えたり、本文を削りすぎたりしうる。prompt-template spec より前からある。直すときは、キーにモデル(またはプロバイダと endpoint)を含めるか、AI 接続設定が変わったときにクリアする。
  2026-11-12(llama-server-provider spec の統合検証)に、一部を直した。`llamaServerStore` が、`llama-server` が準備完了になったとき(起動のたび)と、「現在使うプロバイダ」が変わったときに `clearContextBuilderCache` を呼ぶ(`architecture.md`「llama-server プロバイダ」の「トークン数の計測」)。残っているのは、同じプロバイダのまま OpenAI 互換の接続先やモデル名を変えたとき(推論サーバーの側でモデルを読み込み直したときを含む)。
- [ ] **推論モデルで本文が空のまま終わりうる**(触発元: 上記 gpt-5 系 400 の調査 2026-10-22)
  推論モデルの `max_completion_tokens` には推論トークンも含まれる。既定の maxTokens(200)では推論だけで上限に達し、本文が空のまま `finish_reason: "length"` で終わる可能性が高い。当面の回避策は 2 つ。maxTokens を大きくするか、`extras` に `reasoning_effort` を書く(gpt-5 は `minimal`、5.1 以降は `none` が使える)。`reasoning_effort` を自動で付けることは見送った。指定できる値がモデルごとに違い(gpt-6-astra は `none` 不可など)、判定がずれると別の 400 を生むため。推論モデル向けの maxTokens の既定値や、effort を選べる UI を含めて検討する。

### アプリ側の設定 / llama-server プロバイダ

- [ ] **壊れた `preferences.json` が、次の保存で空の内容から上書きされる**(触発元: llama-server-provider spec の統合検証 2026-11-12)
  `preferences.json` が JSON として壊れている・オブジェクトでないとき、`parsePreferences` は全体を空として扱う(`architecture.md`「llama-server プロバイダ」の「設定の置き場所」)。そのまま AI 設定画面で何かを入力するか、左ペインでモデルを選ぶと、空の内容に入力した分だけを足したものでファイルを上書きし、壊れる前の内容(実行ファイルのパス、モデルごとのコンテキスト長、将来のほかのアプリ設定)は取り出せなくなる。手で編集して括弧を 1 つ壊しただけでも起きる。書き手には何も知らせていない。直すときは、解析に失敗したら元のファイルを別名で退避してから書くか、保存を止めて壊れていることを知らせる。
- [ ] **初期化が終わる前の要求で誤った案内が出うる。フォルダが応答しないと UI が止まりうる**(触発元: llama-server-provider spec の統合検証 2026-11-12)
  2 つある。(1) アプリの起動時の `initLlamaServerStore`(設定の読み込みと一覧の作成)が終わる前に提案や情景文を要求すると、ストアはまだ既定値なので、設定済みでも「llama-server の実行ファイルが設定されていません」などの案内が出る。起動の直後に限られるが、モデルのフォルダの読み取りが遅いと窓が広がる。直すときは、初期化が済むまで関門が「準備中」として断るか、初期化を待つ。(2) Rust の `list_gguf_models` / `write_app_preferences`(と `read_app_preferences`)は同期の command で、UI のスレッドで動く。モデルのフォルダが応答しないネットワークドライブや、スピンアップ待ちのディスクを指していると、その間ウィンドウが固まる。`list_gguf_models` は、起動時・左ペインの展開・起動の直前にも呼ぶようになったので、当たる機会が増えた。直すときは、`async` の command から `spawn_blocking` で呼ぶ(`start_llama_server` / `stop_llama_server` と同じ形)。
- [ ] **左ペインのモデル名が途中で切れ、量子化の違いが見分けにくい**(触発元: llama-server-provider spec の実機確認、2026-11-12)
  左ペインは幅が狭く、モデルのファイル名は省略表示になる。`gemma-4-31B-it.IQ4_XS.gguf` と `…Q4_K_S.gguf` のように、名前の後ろだけが違うファイルは、どちらも `gemma-4-31B-it...` と出て見分けられない。「コンテキスト長未設定」の印が付く行は、さらに短くなる。マウスを載せれば全体が出るが、量子化の切り替えがこの一覧の主な用途なので、違いが出る後ろ側を残す(前を省く、2 行にする、共通の頭を省く など)ほうがよい。状態の行とファイル名の行で左端が揃っていない点も、あわせて直す。

## バックログに入れない方針のもの

差別化軸を歪めるため意図的に取らない磨き込みの方針は `roadmap.md` の「採らない方針」が正。同じ判断軸を本ファイルでも参照する(=「ここに磨き込みとして書きそうになったら、まず roadmap の方針に該当しないかを確認する」関門)。
