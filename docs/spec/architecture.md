# Sumire — アーキテクチャ仕様

本書は MVP のシステム構成・モジュール分割・データ形式を定める。実装はこの仕様に従う。

## プロセス構成

```
┌──────────────────────────────────┐    ┌────────────────────────────┐
│   Sumire アプリ (Tauri)           │    │ 推論サーバー (外部プロセス) │
│ ┌──────────────────┐             │    │                            │
│ │ Frontend         │             │    │  text-generation-webui の  │
│ │ React + TS       │             │    │  --api モードを利用        │
│ │ (CodeMirror 6)   │             │    │                            │
│ └────────▲─────────┘             │    │  OpenAI 互換 HTTP API を   │
│          │ IPC (invoke / Channel)│    │  公開                      │
│ ┌────────▼─────────┐             │    │                            │
│ │ Native (Rust)    │◄────HTTP────┼───►│  例: http://127.0.0.1:5000 │
│ │ Tauri commands   │             │    │      /v1/...               │
│ └──────────────────┘             │    │                            │
└──────────────────────────────────┘    └────────────────────────────┘
```

推論サーバー・クラウド API(OpenAI 等)への HTTP は、どちらも Native(Rust)側から出す。Frontend は IPC で Rust に中継を頼み、応答のチャンクを Channel で受け取る(詳細は「IPC 境界」節)。

上の図は、書き手が起動した推論サーバーにつなぐ形(OpenAI 互換プロバイダ)。`llama-server` プロバイダでは、推論サーバーを Sumire の Native(Rust)側が子プロセスとして起動する。推論が別プロセスで、HTTP で話すことは同じ。

```
┌──────────────────────────────────┐    ┌────────────────────────────┐
│   Sumire アプリ (Tauri)           │    │ llama-server (子プロセス)  │
│ ┌──────────────────┐             │    │                            │
│ │ Frontend         │             │    │  書き手が用意した          │
│ │ React + TS       │             │    │  llama.cpp の実行ファイル  │
│ └────────▲─────────┘             │    │                            │
│          │ IPC (invoke / Channel │    │  127.0.0.1 の空きポートで  │
│          │      / イベント)      │    │  待ち受ける                │
│ ┌────────▼─────────┐  起動・停止 │    │                            │
│ │ Native (Rust)    │─────────────┼───►│  /health  /props           │
│ │ Tauri commands   │◄────HTTP────┼───►│  /tokenize                 │
│ │ 子プロセスの監督 │             │    │  /v1/completions           │
│ └──────────────────┘             │    │                            │
└──────────────────────────────────┘    └────────────────────────────┘
```

### 推論サーバーの管理

推論サーバーを誰が起動・停止するかは、プロバイダごとに違う。

| プロバイダ | 起動・停止の主体 | 接続先とモデルの決め方 |
|---|---|---|
| OpenAI 互換(`openai-compatible`) | 書き手。Sumire は起動も停止もしない | 接続先 URL とモデル名を `sumire.json` に書く |
| llama.cpp(`llama-server`) | Sumire。書き手が指した `llama-server` を子プロセスとして起動し、要らなくなったら止める | 接続先は Sumire が起動のたびに決める。モデルとコンテキスト長はアプリ側の設定(`preferences.json`)で決める |
| OpenAI(`openai`) | —(クラウドの API。推論サーバーは無い) | 接続先 URL とモデル名を `sumire.json` に書く |

- OpenAI 互換プロバイダの推論サーバーは、今までどおり Sumire の管理外。Sumire の起動時にプロセスを起動したり、終了時に停止したりはしない。
- `llama-server` プロバイダでは、Sumire が起動したプロセスだけを扱う。Sumire が起動していない `llama-server`(text-generation-webui が内部で起動したものなど)は、検出も再利用も停止もしない。そこにつなぐには OpenAI 互換プロバイダを使う。
- どちらの場合も、推論は Sumire とは別のプロセスで動き、Sumire は HTTP で話す。推論エンジンをプロセス内に組み込まない(`vision.md`「設計哲学」)。

**改めた経緯(2026-11-12、`llama-server-provider` spec)**: それまでは「推論サーバーは Sumire の管理外。書き手が手動で起動・停止する」を全プロバイダの前提にしていた。推論サーバーの起動オプション(モデル選択、量子化、GPU 設定など)が多岐にわたり、Sumire 側での管理は MVP のスコープを超える、という理由だった。この前提を、OpenAI 互換プロバイダに限るものに改めた。理由は次の 3 つ。

- 量子化(Q3_K_M / Q5_K_M など)を切り替えるたびに、text-generation-webui の画面でモデルを読み込み直して Sumire に戻る手間があった。
- 推論サーバーの側のコンテキスト長と `sumire.json` の `contextWindow` を手で揃えていた。ずれると、本文が無駄に削られるか、推論サーバーの側であふれる。
- 推論サーバーをほかのアプリに任せていると、新しいモデルや llama.cpp の更新を取り込む時機を、Sumire の側で選べない。

Sumire が受け持つのは、モデルのファイル・コンテキスト長・追加の起動引数を渡して起動し、止めるところまで。汎用のモデル管理(ダウンロード、一覧の整理、モデルごとの細かな調整)はしない(`roadmap.md`「採らない方針」)。詳細は本書「llama-server プロバイダ」。

### 接続喪失時の挙動

- 推論サーバーへの常時 ping(ヘルスチェック)は行わない。
- 提案要求時に接続失敗した場合、エラーをトーストで表示する。
- 本文編集・保存などの非 AI 機能は推論サーバーの状態に関わらず使用できる。
- `llama-server` プロバイダでは、起動してから準備完了になるまでの間だけ、Rust 側が `/health` を 0.5 秒おきに呼んで、読み込みが終わったかを確かめる。準備完了のあとは、通信で確かめない。プロセスが終了したことは、HTTP ではなく子プロセスの見張り(0.25 秒おきの終了の確認)で分かり、状態の知らせとして書き手に伝える(本書「llama-server プロバイダ」の「状態」)。

## IPC 境界(フロント/Rust の責務分担)

### 基本方針

- **ファイル I/O 系は Rust 側に集約**する。理由はパス制御とエラーハンドリングの一貫性、および Tauri のセキュリティモデルとの整合
- **HTTP リクエストは Rust 側が担う**。フロントのアダプタは `nativeFetch`(`src/domain/http/`)を `fetch` と同じ形で呼び、`nativeFetch` が `http_request` を invoke する。Rust 側(`commands/http.rs`、reqwest)が送受信し、応答を Channel でチャンクごとに流す。`nativeFetch` はそれを Web 標準の `Response` に組み立てて返す。Rust 側の責務は「送る・流す・切る・キーを付ける」に絞り、SSE の解釈・ステータスによるエラー分類・タイムアウト判定はフロントのアダプタに残す。理由は次の 2 つ:
  - **推論サーバーのアクセス元制限**: text-generation-webui v4.x などは、既定でアクセスを許す Origin を `localhost` / `127.0.0.1` に絞る。リリースビルドの WebView の Origin は `http://tauri.localhost` なので、WebView の `fetch` は CORS で拒否される(開発ビルドの `http://localhost:1420` は通るため、リリースビルドでだけ「接続できません」になる)。Rust 側の通信は CORS の判定を受けない。
  - **API キーを画面側に渡さない**: キーは Rust 側で OS の資格情報ストアから読み出し、`Authorization` ヘッダーに付けて送る。フロントはリクエストにプロバイダ名(`authProvider`)を指定するだけで、キーの値を取得する command は無い(キーについてフロントが読めるのは、設定済みかどうかを返す `has_secret` だけ。保存・削除は `set_secret` / `delete_secret`)。
  - **キーを付ける相手を固定する**: 接続先(`sumire.json` のエンドポイント)は作品ごとの設定で、他人から受け取ったプロジェクトにも書ける。キーは PC ごとの資格情報ストアにあるので、接続先を検査せずに付けると、開いたプロジェクトしだいでキーが第三者のサーバーに渡る。そこで Rust 側(`commands/http.rs` の `auth_host_allowed`)が、キーを付ける相手をプロバイダごとに固定する。`openai` は `https://api.openai.com`(既定のポート)だけ。それ以外の接続先では、キーを読まずに開始時エラー(`authHostNotAllowed`)を返し、HTTP は送らない。画面側は「この接続先には API キーを送れません」と伝える。キーを付けないリクエスト(OpenAI 互換と `llama-server`)の接続先は制限しない。

  経路のオーバーヘッドは、最初の SSE イベントまでの時間で WebView `fetch` の中央値 4ms に対し 5ms(実測)で、実用上の差はない。

  採らなかった代替案:
  - **推論サーバー側の `--listen` / `--public-api`**: `--listen` は全インターフェースで待ち受けるので API が LAN に露出し、`--public-api` はインターネットに公開してしまう。どちらも、書き手にサーバーの起動オプションの変更を強いる。
  - **tauri-plugin-http**: CORS は回避できるが、ヘッダーを JS 側で組み立てるため、キーを画面側に渡さない方針と噛み合わない。

  経緯と実測は、`provider-http-rust` spec の作業記録(公開しているリポジトリには含めていない)にある。

| ローカルログ書き込み | Rust | ファイル I/O |
| 推論サーバー・クラウド API への生成リクエスト | Rust (`http_request`、フロントの入口は `nativeFetch`) | HTTP。CORS の判定を受けず、キーを Rust 側で付けるため |
| 推論サーバーへのトークン数問い合わせ | Rust (同上) | 同上 |

| `llama-server` の `/props` の解釈(実際に確保されたコンテキスト長) | フロント(`llamaServerStore`。通信は `nativeFetch` 経由) | 応答の中身の意味づけはフロントに残す |
| `llama-server` をいつ起動し、いつ止めるかの判断 | フロント(`llamaServerStore`) | 提案要求・モデルの選択・プロバイダの切り替えなど、UI の出来事で決まるため。Rust は命令された起動と停止を行うだけ(アプリの終了時の停止だけは Rust が自分で行う) |
| エディタの状態管理・UI ロジック | フロント | UI 層 |
| 提案候補の管理(複数案保持・サイクル) | フロント | UI 層 |
| ContextBuilder(プロンプト構築) | フロント | ファイル内容を Rust から取得した後の純粋ロジック |

### Tauri commands の命名規約

- snake_case を採用する
- 動詞 + 対象の順: `read_project`, `save_chapter`, `list_chapters`, `move_to_trash`, `create_chapter`, `rename_chapter`, `save_snapshot`, `list_snapshots`, `restore_snapshot`, `read_recent_projects`, `update_recent_projects` 等
- フロント側からは `invoke('read_project', { path })` で呼び出す
- 例外: HTTP 中継の `http_request` / `http_cancel` は、操作対象ごとに分かれない汎用の中継なので、`http_` を前置した形にしている
- `llama-server` プロバイダの command(2026-11-12、`llama-server-provider` spec)も同じ規約に従う。引数と戻り値の形は本書「llama-server プロバイダ」
  - `start_llama_server` / `stop_llama_server`: 起動と停止。どちらも新しい状態を返す
  - `read_llama_server_status` / `read_llama_server_log`: 今の状態と、出力の末尾の読み出し
  - `read_app_preferences` / `write_app_preferences`: `preferences.json` の読み書き(文字列)
  - `list_gguf_models`: フォルダの直下の gguf の一覧
- Rust からフロントへの知らせには Tauri のイベントを使う。今あるのは `llama-server-status`(`llama-server` の状態が変わるたびに、新しい状態を全ウィンドウに送る)の 1 つ

## プロバイダ抽象

### 役割

`AIProvider.generate(request)` は **`request.body` の続きを生成する** API である。
チャット応答ではない。Sumire は AI と会話するツールではなく、
本文の続きをゴーストテキストとして提案するツールであるため、
ここでの契約は「テキストの続きを返す」に固定する。

### Chat ではなく Completion を使う(MVP)

`OpenAICompatibleAdapter` は内部で **`/v1/completions`(レガシー補完)** を叩く。
`/v1/chat/completions` は使わない。理由:

- Instruct チューニング済みモデル(初期検証の `japanese-stablelm-instruct-alpha-7b-v2` を含む)を
  Chat 経路で使うと、直前本文を「ユーザー発言」として解釈し、
  「了解しました」「・・・」のような短い応答や、入力のオウム返しを返してしまう。
- Web 小説の続き生成は「テキストの末尾に続きを足す」操作であり、レガシー補完の意味論と一致する。
- 本書「文脈管理モジュール (ContextBuilder)」節のコンテキスト構築の優先順位(システム → 設定 → 本文 → 生成余地)は、最終的に 1 本のプロンプト文字列に直列化して `/v1/completions` の `prompt` に渡す。

将来 Claude / Gemini など Chat 系しか提供しないプロバイダのアダプタを実装する場合は、
そのアダプタ内部で chat メッセージへの変換(「以下の本文の続きを書いてください」のような
指示プロンプト + 直前本文の構造)を行い、`AIProvider.generate` の契約
(=テキストの続きを返す)を守ること。

### プロンプトテンプレート

指示チューニング専用のモデルの中には、素の連結(本書「プロンプト直列化の改行ルール」)のプロンプトでは続きを書けず、出力が崩れるものがある。ローカルの Completion のプロバイダ(OpenAI 互換と `llama-server`)では、`sumire.json` の `template`(本書「`sumire.json`」節)にプロンプトテンプレートを指定すると、システムプロンプト・設定・本文をテンプレートの差し込み口に入れた 1 本の文字列を、`/v1/completions` の `prompt` として送る(2026-11-04、`prompt-template` spec)。送り先は Completion のままで、Chat API には切り替えない。`template` が無ければ、導入前と同じ素の連結で送る。

**指定の入口**: 内蔵プリセットと「指定なし」は、AI 設定画面の「プロンプトテンプレート」の欄(`ux.md`「AI 接続設定 UI」)で選ぶ。選んだ時点で `sumire.json` に保存し、プロジェクトを開き直さなくても次の提案から効く(2026-11-16、`template-settings-ui` spec)。自由記述(`custom`)は、引き続き `sumire.json` の直接編集で書く。

- 当初(`prompt-template` spec)は、テンプレートを AI 設定画面に出さず、`sumire.json` の直接編集だけで指定する形にしていた。公開後、初めて使う書き手には設定の存在が分からず、指示に答える形で学習されたモデルで出力が崩れる原因になっていたので、2026-11-16 に画面から選べる形に改めた。テンプレートの書式、プリセットの中身、解決と描画の規則は変えていない。
- 画面の判断(いまの指定を「指定なし / プリセット / 自由記述 / 読めない指定」に分ける、選択肢から保存する値を作る、プリセットごとの付帯情報)は `domain/providers/templateSelection.ts` が持つ。指定の解釈は `resolvePromptTemplate` の結果から導き、独自に解釈し直さない。`promptTemplate.ts` から `templateSelection.ts` への依存は作らない。
- 保存は `aiConfigStore` の `saveTemplateSelection` で行う。セクションの `template`(と、思考を分けるタグを足すときだけ `thinking`)を置き換えて保存し、成否を返す。保存に失敗したら、そのセクションの `template` と `thinking` だけを呼ぶ前の値に戻す(保存の失敗のトーストは、ほかの AI 設定の保存と同じ)。
- 提案コントローラは、要求のたびにストアからセクションを読み、テンプレートを解決し直す。生成中の要求は、開始時に解決したテンプレートを持ち回る。したがって、画面で選び直すと次の要求から効き、生成中の提案には影響しない。提案コントローラは変えていない。
- 思考ありのプリセット(`gemma4-think`)を選ぶと、思考を分けるタグの組を `thinking.tags` に足す(下の「プリセットの中身」の `gemma4-think` の項)。

**適用位置**: 提案コントローラが、提案要求のたびに、生成を始める前(生成中の表示を出す前)に `resolvePromptTemplate(config.template)`(`domain/providers/promptTemplate.ts`)でテンプレートを解決する。`template` を読む口はこの関数に限る。解決するのは、プロバイダがローカルの Completion のプロバイダ(OpenAI 互換と `llama-server`。判定は `domain/providers/types.ts` の `isLocalCompletionProvider`)のときだけで、OpenAI プロバイダ(クラウド)では `template` が書かれていても読まず、挙動を変えない。`llama-server` を対象に加えたのは 2026-11-12(`llama-server-provider` spec)で、規則とプリセットは変えていない。解決済みのテンプレートは、ContextBuilder(トークン予算の計算、本書「コンテキスト構築の優先順位」)と `GenerationRequest.promptTemplate` の両方に渡す。差し込み口に内容を入れるのは `OpenAICompatibleAdapter`(それを継承する `LlamaServerAdapter` も同じコードを通る)で、`renderPromptTemplate` を使う。

- 差し込む内容は、素の連結のときと同じにする。システムプロンプトは前後の空白を除いたもの(既定のシステムプロンプトの適用も今のまま)、設定は本書「プロンプト直列化の改行ルール」の規則でつないだもの、本文はルビを剥がしたもの。
- `template` も解決済みのテンプレートも、リクエストの項目としては送らない。送るのは包んだ結果の `prompt` だけ。モデル名・パラメータ・`extras`・ストリーミングの扱いも変えない。
- 応答の扱い(思考の分離・ゴースト・採用・メモ転記・暗黙のキャンセル)は変えない。

**差し込み口**:
- `{{system}}`(システムプロンプト)、`{{settings}}`(設定)、`{{body}}`(本文)の 3 つ。照合は大文字小文字を区別する完全一致。`{{ system }}` のような揺れや、ほかの `{{…}}` は、文字列としてそのまま送る。打ち間違い(`{{sytem}}` など)も検出されず、そのまま送られる。
- `{{body}}` は必ず 1 つ書く。どの差し込み口も 2 つ以上は書けない。
- `{{system}}` と `{{settings}}` は省ける。省いた差し込み口の内容はプロンプトに含めず、トークン予算でも数えない。設定として送る内容が無ければ、`{{settings}}` には空文字列が入る。
- `{{body}}` の後ろに文字があってよい(`gemma4-think` のように、本文の後ろにモデルの番の開始を置く書き方)。
- テンプレートの文字列は書き換えない(改行の正規化も trim もしない)。差し込んだ内容の中に `{{…}}` があっても、再解釈しない。テンプレートの文字列と差し込み口の内容のほかに、文字を足さない。
- BOS はテンプレートに含めない。今と同じく推論サーバーが付ける。区切り(`<|turn>` や `<|im_start|>` など)は、推論サーバーがモデルの特殊トークンとして解釈することを前提にする。

**本文の位置と思考の有無**:
- 思考なしのテンプレート(`gemma4` / `chatml` / `chatml-nothink`)は、本文をモデルの番の最後に置く。本文がプロンプトの最後になり、後ろには何も付けないので、生成された続きがカーソル位置からそのままつながる。システムプロンプトと設定は本文より前に置く。
- 思考ありのテンプレート(`gemma4-think`)は、本文を user の番に置き、プロンプトをモデルの番の開始で終える。思考はモデルの番の先頭で行われるため。本文をモデルの番に先に埋めて思考をオンにすると崩れた(下の実測)。モデルが書きかけを言い直してから続けることがありうる。そのときは書き手が採用後に手で削る。

**内蔵プリセット**: 名前で選ぶ(`{ "preset": "gemma4" }`)。名前は大文字小文字を区別する完全一致。定義は `domain/providers/promptTemplate.ts` の `PROMPT_TEMPLATE_PRESETS`。

| 名前 | 書式 | 思考 | 本文の位置 |
| --- | --- | --- | --- |
| `gemma4` | Gemma 4 | なし(モデルの番の頭に空の思考チャンネルを置く) | モデルの番の最後(プロンプトの最後) |
| `gemma4-think` | Gemma 4 | あり(system の番の頭で思考を有効にする) | user の番(プロンプトはモデルの番の開始で終わる) |
| `chatml` | ChatML | 先埋めなし | assistant の番の最後(プロンプトの最後) |
| `chatml-nothink` | ChatML | 止める(空の思考ブロックを先に埋める) | assistant の番の最後(プロンプトの最後) |

各プリセットの中身は次のとおり。コード片の行の切れ目は改行(`\n`)1 つを表す。最後の行の後ろには、`gemma4-think` だけ改行が 1 つ付き、ほかの 3 つは何も付かない(`{{body}}` で終わる)。

`gemma4`:

```
<|turn>system
{{system}}<turn|>
<|turn>user
{{settings}}<turn|>
<|turn>model
<|channel>thought
<channel|>{{body}}
```

`gemma4-think`(最後の `<|turn>model` の後ろに改行が 1 つ付く):

```
<|turn>system
<|think|>{{system}}<turn|>
<|turn>user
{{settings}}

{{body}}<turn|>
<|turn>model
```

`chatml`:

```
<|im_start|>system
{{system}}<|im_end|>
<|im_start|>user
{{settings}}<|im_end|>
<|im_start|>assistant
{{body}}
```

`chatml-nothink`:

```
<|im_start|>system
{{system}}<|im_end|>
<|im_start|>user
{{settings}}<|im_end|>
<|im_start|>assistant
<think>

</think>

{{body}}
```

- `gemma4-think` で設定が空のときは、user の番が `\n\n` + 本文で始まる。
- `gemma4-think` の応答は `<|channel>thought\n…<channel|>` で始まる。text-generation-webui(llama.cpp loader)では、ストリーミングでも `<|channel>` と `<channel|>` がそれぞれ 1 つのチャンクとして文字列で届くことを確かめた(2026-11-04)。思考を本文と分けるには、`thinking.tags`(本書「`sumire.json`」節)に `{ "open": "<|channel>", "close": "<channel|>" }` が要る。無ければ、思考は分離されずに本文としてゴーストに出る。`thinking.tags` に有効な組が 1 つでもあると既定の `<think>` の組は使われなくなるので、ほかのモデルと共用するなら両方を並べる。
  - AI 設定画面で `gemma4-think` を選ぶと、Sumire がこの組を `thinking.tags` に書き足して保存する(2026-11-16、`template-settings-ui` spec)。今ある組は消さず、並びも変えずに後ろへ足す。有効な組が 1 つも無いとき(`thinking` が無いときを含む)は、既定の `<think>` の組も一緒に書く(`<think>` の分離が外れないように)。組がすでにあれば書き換えない。
  - 思考の分離が無効(`enabled: false`)なら、足さず、有効にもしない。画面に、思考の文が提案に混ざることを注記で出す。
  - ほかのプリセットや「指定なし」に選び直しても、足した組は消さない。`gemma4-think` 以外の選択肢では、`thinking` を書き換えない。
  - 思考の分離の設定は続き提案と挿し絵の情景文で共通なので、足した組は挿し絵の情景文の思考の分離にも効く。手で書き足したときと同じ結果になる。
  - `sumire.json` を直接編集して `gemma4-think` を指定したときは、これまでどおり書き手が組を書き足す。
  - 当初(`prompt-template` spec)は、テンプレートと思考の分離の設定を独立させ、テンプレートがタグの組を自動で足すことはないとしていた。画面から選べる形にしたときに、選ぶだけで思考が本文と分かれるよう改めた。分離の規則(`resolveThinkingTags`、`thinkingSplitter.ts`)は変えていない。
- `gemma4-think` は思考に約 1,900〜2,300 字(英語)を使う。2026-11-04 の実測(gemma-4-31B-it Q4_0、RTX 5090、約 28 tok/s)では、思考と本文を合わせて 1,800 トークンに約 64 秒かかり、既定の `timeoutMs`(60000)ではタイムアウトした。`maxTokens` は 1,800 前後、`timeoutMs` は 120000 程度にする。AI 設定画面は、`gemma4-think` が選ばれていて Max Tokens が 1000 未満のとき、思考の分も Max Tokens に含まれることと、値を上げることを勧める案内を出す。値は書き換えない(Max Tokens とタイムアウトは書き手が決める)。
- `chatml` は、思考しない ChatML のモデルの基本形。思考する ChatML のモデルには使わない。2026-11-04 に、思考する ChatML のモデル(Qwen3.8-27B ベースの fine-tune)で試すと、数文字(0〜17 字)を書いたところで `<|im_end|>` を出して番を終え、アプリでは「応答が空です」になった(ストリーミング・非ストリーミングとも、各 2 本以上)。思考する ChatML のモデルには `chatml-nothink` を使う。
- `chatml-nothink` は、2026-11-01 に Qwen3.8-27B ベースの fine-tune で、思考なしで品質が一番良かった形(空の思考ブロックを先に埋めてから本文を置く)。
- ChatML の 2 つは、2026-11-04 の時点で ChatML のモデルでは実測していない。崩れた場合はプリセットの中身を直す(`sumire.json` の形は変えない)。

自由記述のテンプレート(`{ "custom": … }`)は、プリセットに無いモデルのために書き手が書く。差し込み口の規則はプリセットと同じで、プリセットも同じ解析を通る。

**不備の扱い**: テンプレートの指定に不備があれば、生成を始める前にトーストで伝え、提案を生成しない。生成中の表示もゴーストも出さない。素の連結に黙って戻すと、崩れた出力が出て原因が分からなくなるため。不備の判定は提案要求のたびに行い、`sumire.json` の読み込み時にはトーストを出さない。

| 不備 | 当たる値 | トースト(ja) |
| --- | --- | --- |
| 読めない形 | オブジェクトでない(配列を含む)、`preset` と `custom` の両方がある・どちらも無い、`preset` が文字列でない、`custom` が文字列でも文字列の配列でもない | テンプレートの指定を読めません。sumire.json の template には preset か custom のどちらか一方を書いてください |
| 未知のプリセット | `preset` が内蔵プリセットの名前に無い | テンプレートのプリセット「{{name}}」はありません。使えるのは gemma4 / gemma4-think / chatml / chatml-nothink です |
| 本文の差し込み口なし | テンプレートに `{{body}}` が無い(`custom` の空配列も、空文字列としてここに入る) | テンプレートに本文の差し込み口 {{slot}} がありません |
| 差し込み口の重複 | いずれかの差し込み口が 2 つ以上ある | テンプレートに差し込み口 {{slot}} が 2 つ以上あります |

- 文言は `ja.json` の `toast.templateUnreadable` / `toast.templatePresetUnknown` / `toast.templateMissingBody` / `toast.templateDuplicateSlot`。`{{name}}` には指定されたプリセットの名前、`{{slot}}` には差し込み口の表記(`{{body}}` など)が補間値として入る。差し込み口の表記を文言に直接書くと、i18n の補間記法と衝突するため。
- 重複と本文なしの両方に当たるときは、重複として伝える。重複で伝えるのは、左から見て最初に 2 つ目が現れた差し込み口。
- `null` は「テンプレートなし」として扱う(JSON で明示的に外す書き方)。`preset` / `custom` 以外のキーは無視する。
- テンプレートで包んだ後に推論サーバーが返したエラー(HTTP 400 など)は、ほかの生成エラーと同じ扱い。

**根拠(2026-11-04 の実測)**: text-generation-webui v4(llama.cpp loader)の `gemma-4-31B-it` に、書き手の設定と本文(約 1,350 トークン)を送って比べた。形ごとに多くは 2 本。

- 素の連結(導入前の Sumire)は、温度 0 でも数十字で反復に崩れた。
- Chat API(`/v1/chat/completions`)は、思考のあと正常に続くが、書きかけを言い直して始める。Chat API で assistant を先に埋める形(`continue_`)は 21 トークンで止まった。
- 本文をモデルの番に先に埋める形は、モデルの番の頭に空の思考チャンネル(`<|channel>thought\n<channel|>`)を置くと正常に続き、置かないと崩れた。システムプロンプトを system の番に置く形でも、設定が空の形でも正常だった(`gemma4` の形)。
- 思考をオンにして本文をモデルの番に先に埋めると崩れた。本文を user の番に置き、モデルの番を空で始めると、思考のあと書きかけから言い直さずに続いた(`gemma4-think` の形)。
- Gemma 4 の区切り(`<|turn>` `<turn|>` `<|channel>` `<channel|>` `<|think|>`)は、それぞれ 1 トークンとして扱われた(Gemma 3 の `<start_of_turn>` は 1 トークンにならない)。BOS はサーバーが自動で付け、プロンプト中に `<bos>` を書いても重複しなかった。

詳細は、`prompt-template` spec の作業記録(公開しているリポジトリには含めていない)にある。

### コンテキストセクションのラベル取り扱い

`ContextSection.label`(例: `"キャラ設定: すみれ"`)は、`OpenAICompatibleAdapter` の
プロンプト直列化では **使わない**。本文(`content`)だけを空行で連結する。

理由:

- Instruct 系の小規模ローカル LLM はプロンプト中の見出し(`# キャラ設定: …`)に強く引きずられ、
  生成側にも同様の見出しや書式パターンを盛ってくる傾向がある。
- 書き手が「設定ファイルにどう見出しを付けるか」を自分で制御できる方がよい。
  Sumire 側で固定見出しを押し付けるとコントロールを奪う。
- ファイルの粒度(1 キャラ 1 ファイル / まとめて 1 ファイル)も書き手に委ねる方針(`ux.md` の設定タブ節参照)。

`label` 自体は削除せず、ログ用および将来の chat 系アダプタ(=メッセージ整形時に
ラベル情報が必要)のためにデータとしては保持する。

挿し絵の情景文の経路だけは、この方針の例外として、設定と本文のまとまりに Sumire が固定の見出しを付けて送る(本書「挿し絵の情景文」)。例外はその経路に限り、続き生成のプロンプトには持ち込まない。

### インターフェース

```typescript
interface AIProvider {
  /**
   * request.body の続きを生成する(チャット応答ではない)。
   * Sumire は AI と会話するツールではなく、本文の続きを提案するツール。
   */
  generate(request: GenerationRequest): Promise<GenerationResponse>;

  /** 複数候補の並列生成(MVP は内部で generate を N 回並列実行) */
  generateMultiple(
    request: GenerationRequest,
    n: number
  ): Promise<GenerationResponse[]>;

  /** トークン数を計測する。プロバイダの API を介して正確な値を返す */
  countTokens(text: string): Promise<number>;
}

interface GenerationRequest {
  systemPrompt: string;
  contextSections: ContextSection[]; // 設定情報など、構造化された前置き
  body: string;                       // プロンプト末尾(=直前の本文)。AI はこの続きを返す
  parameters: GenerationParameters;
  promptTemplate?: ParsedPromptTemplate; // 解決済みのテンプレート。OpenAI 互換アダプタと、それを継承する llama-server のアダプタが使う(本書「プロンプトテンプレート」)
}

interface ContextSection {
  label: string;       // 例: "キャラ設定: アリス"
  content: string;
}

interface GenerationParameters {
  temperature: number;
  topP: number;
  maxTokens: number;
  // モデル固有の追加パラメータは extras: Record<string, unknown> で吸収
  extras?: Record<string, unknown>;
}

interface GenerationResponse {
  text: string;
  finishReason: "stop" | "length" | "error";
  usage?: { promptTokens: number; completionTokens: number };
}
```

### OpenAI アダプタのパラメータの送り分け

`OpenAIAdapter` は `GenerationParameters` を、モデル系統ごとに次のように送り分ける(2026-10-22 決定)。

| 経路 | 対象モデル | 出力上限 | temperature / top_p |
| --- | --- | --- | --- |
| Chat(`/v1/chat/completions`) | 非推論モデル(gpt-4o 系など) | `max_completion_tokens` | 送る |
| Chat(`/v1/chat/completions`) | 推論モデル | `max_completion_tokens` | 送らない |
| Completion(`/v1/completions`) | `-instruct` 系 | `max_tokens` | 送る |

- **推論モデルの判定**: `-instruct` 判定と同じく、モデル名の前方一致で行う。`gpt-N`(N ≥ 5)と `o` + 数字(o1 / o3 / o4-mini など)を推論モデルとみなす。gpt-5-chat-latest のような非推論の派生も推論モデル側に入れる。誤判定しても temperature が効かなくなるだけで、HTTP 400 にはならないため。
- **Chat 経路は全モデルで `max_completion_tokens` に統一する**: 公式リファレンスで `max_tokens` は deprecated とされ、o-series とは互換性がないと明記されている。推論モデルは `max_tokens` を HTTP 400 で拒否する。
- **推論モデルには temperature / top_p を送らない**: 推論モデルは既定値以外を拒否することがある(初代 gpt-5 は temperature = 1 しか受け付けない。新しいモデルも reasoning effort が `none` 以外だと拒否する)。AI 設定画面では、OpenAI で推論モデルを選んでいるときに「送信しない」旨の注記を出す。値は編集できるままにする。
- **`extras` は常に最後に上書きする**: reasoning effort を `none` にして temperature を効かせたい場合などは、`sumire.json` の `extras` に書けばそのまま送られる。
- Completion 経路(`/v1/completions`)には `max_completion_tokens` が無いため、`max_tokens` のまま送る。

出典: OpenAI API リファレンス「Create chat completion」(`max_tokens` / `max_completion_tokens` の説明)、OpenAI「Using GPT-6」ガイド(移行節の「reasoning effort が `none` 以外のときは temperature / top_p / top_logprobs を外す」)。

### 候補数

常に **1 案**を返す。複数候補のサイクル比較は持たない(M8 で撤去済み)。再生成したい場合は呼び出し側で停止 → 再要求する運用。

### ストリーミング生成

`AIProvider.generateStream(request, signal)` を介して、生成テキストをチャンクで受信できる。

プロトコル(`OpenAICompatibleAdapter` の場合):

- OpenAI 互換 `/v1/completions` に `stream: true` を渡し、Server-Sent Events で受信(`data: {...}\n\ndata: [DONE]\n\n` 形式)
- 各チャンクの `choices[0].text` をその回の差分として連結する
- `AbortController.signal` を `nativeFetch` に渡し、停止経路を確保する。`signal.abort()` → `nativeFetch` が `http_cancel` を呼ぶ → Rust 側が送信タスクを止めて HTTP 接続自体を切断する、の順で止まり、無駄なバイト消費を防ぐ。タイムアウトも、アダプタ内部のタイマーが同じ経路で abort する

将来 Chat 系 API のアダプタを追加する場合も `generateStream` の契約(=`{ textDelta: string }` の async iterator を返す)を守る。

### 思考ブロックの分離

思考モデル(推論モデル)は、応答のテキストに思考ブロック(既定は `<think>`〜`</think>`)を混ぜて返すことがある。提案生成では、これを本文から取り分けてからゴーストに渡す(2026-11-01、`thinking-output` spec)。書き手への見え方は `ux.md`「思考中の表示」、設定は本書「`sumire.json`」節を参照。

**適用位置**: アダプタの契約(本文の続きを、本文のテキストとして返す)は変えない。提案コントローラが、`generateStream` の `textDelta` を純粋な分離器(`domain/providers/thinkingSplitter.ts` の `createThinkingSplitter`)に渡し、分離器が返すスナップショット(ここまでの本文と、思考中かどうか)でゴーストを更新する。分離器は生成ごとに作り、DOM・時刻・i18n に依存しない。タグの組は `resolveThinkingTags(config.thinking)` で決める。`thinking` を読む口はこの関数に限る(直接読むと既定値が効かない)。

**検出**:
- 思考ブロックの外では、いずれかの開始タグが最も早く現れる位置を探す。同じ位置で複数の開始タグが一致したら、長いほうを採る。
- 開始タグから、同じ組の終了タグまでを思考ブロックとする。思考ブロックの中では、ほかの組のタグを探さない。
- 照合は大文字小文字を区別する完全一致。思考ブロックの外に単独で現れた終了タグは、本文として残す。
- 検出は受信した応答に対して行う。思考を取り除いてつないだ後の本文は、走査し直さない。

**保留**(ストリーミング中にゴーストへ出さないもの):
- 思考ブロックの外で、末尾のうち、いずれかの開始タグの真の接頭辞になっている最長部分(例: `<thi`)。タグと確定すれば捨て、タグでないと確定すれば本文に戻す。応答の終わりに残っていれば本文に戻す。
- 本文に改行以外の文字がまだ出ていない間の、先頭の改行。思考ブロックが来れば捨て、本文が来れば戻す。
- 思考ブロックの直後に連続する改行。改行以外の文字が来た時点で、つなぎの規則に従って表示する。
- 思考ブロックの中身は捨てる。保持するのは、終了タグの照合に要る末尾だけ。

**つなぎ**:
- 改行は `\n` だけを数える。継ぎ目の前の本文の末尾に連続する改行の数を a、後の本文の先頭に連続する改行の数を b とする。
- 前後の両方に、改行以外の文字を含む本文がある → 改行を max(a, b) 個にしてつなぐ。思考の前の数文字を捨てると文がつながらなくなるため(実測)、前の本文も残す。
- 応答の先頭(本文より前)の思考ブロック → 接する改行をすべて取り除き、続く本文がカーソル位置から始まるようにする。応答の末尾の思考ブロック → 接する改行をすべて取り除く。
- 改行以外の文字(段落頭の全角スペースを含む)は取り除かない。
- 改行だけを挟んで連続する思考ブロックは、1 つの継ぎ目として扱う。

**終わり方**: 分離器の `finish()` が、思考を除いた本文と、終了タグを受け取らないまま終わったかを返す。終わり方の判定は、最後のスナップショットではなくこの結果で行う。開始タグ同士に接頭辞関係がある組(`<<` と `<<<` など)では、最後のスナップショットが思考中でなくても、思考が終わっていないことがあるため。思考が終わっていなければ、思考の前の本文も含めて提案を出さず、トーストを出す。上限到達かどうかは、チャンクで最後に受け取った `finishReason` が `length` かで判定する。思考を除いて本文が空なら、既存の「応答が空です」にする。停止(`Esc`・暗黙のキャンセル)したときは `finish()` を呼ばない。

**不変条件**:
- タグの組が空(`enabled: false`)なら、保留もしない完全な素通しにする。
- 応答にどの開始タグも現れなければ、確定する本文は受信したテキストの連結に一致する(導入前と同じ)。
- 思考の中身は、画面・ログ・dev 操作ログ・ファイルのいずれにも出さない(例外は下の「開発ビルドのコンソール」)。

**対象外**:
- 思考の中身を書き手に見せること(表示・閲覧・保存のいずれも)
- 思考の分離のためにプロンプトを変えること。プロンプトテンプレート(本書「プロンプトテンプレート」)は思考の分離と独立した機能で、分離の規則も設定も変えない。テンプレートで思考を止めるか(`chatml-nothink` の空の思考ブロックの先埋め)、思考させるか(`gemma4-think`)は、書き手がテンプレートの選択で決める
- 開始タグをプロンプト側に置き、応答に終了タグだけが現れる形の思考(開始タグを出さずに思考するモデル)。内蔵プリセットはこの形を作らない(`gemma4-think` は `<|think|>` で思考を有効にするだけで、思考の開始タグ `<|channel>` は、ストリーミングでも応答に文字列として現れる。2026-11-04 に text-generation-webui で確認)。自由記述のテンプレートでこの形を書いた場合の分離は保証しない。生じた場合は、終了タグが本文に出る
- 本文と別の欄で思考を返す API(Chat API の推論専用フィールド等)。Sumire の生成経路は、その欄を受け取らない
- デバッグ用の単発生成(`AIProvider.generate`、DevTools の `window.__sumire`)。応答をそのまま返す
- maxTokens やタイムアウトの自動調整

**maxTokens の見込み方**: 思考に使ったトークンも maxTokens に含まれる(推論サーバーの挙動)。タイムアウト(`timeoutMs`)も、思考の時間を含めて適用される。実測(Qwen3.8-27B ベースの fine-tune、text-generation-webui)では、思考は約 1,100〜1,300 字の英語で、思考が終わるまで 6〜8 秒かかった(約 40 tok/s なので、思考だけで 250〜320 トークン程度)。既定の 200 では思考の途中で上限に達することがあるので、思考モデルでは maxTokens を 1000 前後に設定する。

**採らなかった案**:

| 案 | 採らない理由 | 再検討の条件 |
|---|---|---|
| 思考を止める(空の思考ブロックを先に埋める、`<think>` を生成禁止にする、`stop` で止める) | 思考ありのほうが場面の組み立てや心理描写が厚く、品質が上がって見えた(各 2 本の比較)。生成禁止は出力が崩れ、`stop: ["<think>"]` は即停止で空の応答になった。空の思考ブロックの先埋めはチャット形式が前提で、プロンプトを変えることになる。2026-11-04 以降は、書き手がテンプレート `chatml-nothink` を選べば先埋めで止められる(本書「プロンプトテンプレート」)。思考の分離の側で思考を止めないことは変えない | 思考を止めても品質が落ちないモデルを主に使うようになったとき。思考の待ち時間が執筆の流れを妨げると分かったとき |
| チャットテンプレート機能(2026-11-04 に採用) | 2026-11-01 の時点では、今のプロンプトのままでも、思考を除けばチャット形式(思考あり)と同等の品質だったので採らなかった。2026-11-04 に、素の連結では崩れるモデル(`gemma-4-31B-it`)で再検討の条件に当たり、`prompt-template` spec でプロンプトテンプレートとして採用した(本書「プロンプトテンプレート」)。テンプレートは書き手が指定したとき(2026-11-16 からは AI 設定画面での選択も含む)だけ使い、指定が無ければ素の連結のままなので、プロンプトに自動で構造を足さない方針(本書「コンテキストセクションのラベル取り扱い」)は保つ | —(採用済み)。開始タグをプロンプト側に置き、応答に終了タグだけが現れる形を内蔵プリセットに加えるときは、分離の規則と適用位置を見直す |
| `/v1/chat/completions` への全面切り替え(2026-11-04) | Chat ではモデルが書きかけを言い直して始めるため、カーソル位置からの連続性を保てない(`gemma-4-31B-it` の実測)。本書「Chat ではなく Completion を使う」の理由もそのまま当てはまる | 主に使うモデルと推論サーバーで、Chat でも書きかけを言い直さずに続くと確かめられたとき。Completion を提供しないプロバイダのアダプタは、本書「Chat ではなく Completion を使う」のとおりアダプタの中で変換する |
| Chat API での assistant の先埋め(text-generation-webui の `continue_`、2026-11-04) | 実測で 21 トークンで止まった(2 本とも同じ文)。`enable_thinking` も効かなかった。先埋めの指定方法が推論サーバーごとに違う | 主に使う推論サーバーで、先埋めした続きが途中で止まらずに出て、指定方法がサーバー間で揃ったとき |
| 各アダプタの中で分離する | アダプタごとに同じ処理を持つことになる。`GenerationChunk` の契約が変わり、両アダプタとそのテストに波及する | 思考を本文と別の欄で返す API に対応し、`GenerationChunk` に思考を運ぶフィールドを足すとき。分離器の適用位置を見直す |

**既知の制約と例外**:
- **終了理由を `text` なしで送るサーバー**: OpenAI 互換アダプタの SSE の解釈は、`choices[0].text` が文字列でないチャンクを `finish_reason` ごと読み捨てる(既存の挙動)。最後のチャンクで `text` を省き、`finish_reason: "length"` だけを送るサーバーでは上限到達を判定できず、上限以外の理由で終わったときのトーストになる。text-generation-webui は最後のチャンクに `"text": ""` を付けて送るので、この制約にかからない(2026-11-01 確認)。OpenAI アダプタの Completion 経路も同じ読み捨て方をする。
- **開発ビルドのコンソール**: OpenAI 互換アダプタと OpenAI アダプタ(Completion 経路・Chat 経路とも)は、開発ビルドで解析できなかった SSE チャンクを `console.warn` に出す(既存の挙動)。そのチャンクに思考の断片が含まれることがある。開発ビルドのコンソールに限られ、ファイルには残らないので許容する。

### MVP で実装するアダプタ

- `OpenAICompatibleAdapter`: OpenAI 互換 HTTP API 全般。text-generation-webui もこれで接続する。

MVP のあとに加えたアダプタ:
- `OpenAIAdapter`: OpenAI のクラウド API(本書「OpenAI アダプタのパラメータの送り分け」)。
- `LlamaServerAdapter`: Sumire が起動した `llama-server`(2026-11-12、`llama-server-provider` spec)。`OpenAICompatibleAdapter` を継承し、生成(`generateStream` / `generate`)は上書きしない。プロンプトの組み立ても SSE の解釈も同じコードを通るので、OpenAI 互換のときに無い文字や構造は足されない。差し替えるのはトークン数の計測(`countTokens`)だけで、`llama-server` の `/tokenize` を使う(本書「llama-server プロバイダ」の「トークン数の計測」)。接続先とコンテキスト長は、呼び出し側が起動中の `llama-server` の状態から組み立てた `AIConfig` として渡す。

将来追加するアダプタ(MVP 外):
- `ClaudeAdapter` (Anthropic API)
- `GeminiAdapter` (Google API)

## 文脈管理モジュール (ContextBuilder)

### 責務

生成リクエスト発行時に、AI に渡すプロンプトを構築する。コンテキスト長制約のもとで何を含め何を省くかを決定する。

### コンテキスト構築の優先順位

コンテキスト窓上限(`aiConfig.contextWindow`、既定 2048。`llama-server` プロバイダでは、`sumire.json` の値ではなく、いま使うモデルに決めてあるコンテキスト長。本書「llama-server プロバイダ」の「コンテキスト長の扱い」)から逆算して以下の順で詰める:

1. **システムプロンプト** (最優先、計測してそのまま使う)
2. **チェック済み設定情報**(`aiConfig.settingsTokenBudget` 既定 500 tok を上限にファイル単位で詰める)
3. **直前の本文**(残り全部、現在編集中の章ファイル内のみ。コンテキスト窓 - システム - 設定 - 生成余地に収まるよう先頭から削る)
4. **生成余地** (`parameters.maxTokens`、既定 200 tok)

プロンプトテンプレート(本書「プロンプトテンプレート」)を使うときは、ContextBuilder が解決済みのテンプレートを受け取り、次のように数える(テンプレートが無ければ上の計算のまま):

- テンプレートの差し込み口以外の文字列を 1 つにつなぎ、そのトークン数を本文枠から引く。本文枠は「コンテキスト窓 - システム - 設定 - テンプレート - 生成余地」になる。
- `{{system}}` が無いテンプレートでは、システムプロンプトを数えない。`{{settings}}` が無いテンプレートでは、設定ファイルを 1 つも詰めない。送らないものに予算を割くと、本文が無駄に削られるため。
- 収まらないときは、テンプレートを使わないときと同じく本文を先頭から削る。テンプレートの文字列は削らない。
- テンプレートの文字列と差し込んだ内容の境目のトークン化で、別々に測った合計と 1〜2 トークンずれることがある。素の連結の区切りの `\n\n` も数えていないので、同じ程度の誤差として許容する。
- 計測値(`usedTokens`)に、テンプレートの分(`template`、テンプレートなしは 0)を持つ。

### 切り詰め方針

- **設定セクション**: ファイル単位。挿入順(=カテゴリ順 → ファイル名順)で詰めて、入らないファイルは丸ごと外す。本文を行/文字単位で切らないことで、設定文書の意味的な完結性を保つ。
- **本文**: カーソル直前の文脈を優先するため **先頭から削る**。文字単位の二分探索でトークン予算ぴったりに収める。

### トークン数計測

プロバイダの `countTokens()` を利用する(モデル固有のトークナイザを通すため)。

- text-generation-webui の場合: `/v1/internal/token-count` 相当のエンドポイントを利用
- `llama-server` プロバイダの場合: `llama-server` の `/tokenize` を利用(本書「llama-server プロバイダ」の「トークン数の計測」)
- モデルによって日本語のトークン消費が 2 倍ほど変動するため、文字数からの雑な推定では不十分
- 設定ファイル本文の計測結果はキャッシュ(`Map<string, number>`)し、連続提案時の API 呼び出しを抑える。テンプレートの差し込み口以外の文字列の計測結果も、同じキャッシュに乗せる(キーは文字列だけ)
- ステータスバー表示用には文字数ベースの推定(係数 1.5)を使い、API 呼び出しは生成リクエスト時のみ

### 章境界の扱い

直前本文として参照するのは **現在編集中の章ファイル内のみ**。前の章は文脈に含めない。

長期的な文脈は設定情報(プロット概要、キャラ設定)で代替する。章をまたぐと話の構造が混ざり生成品質が落ちるため。

### プロンプト直列化の改行ルール

`includeInContext: true` の設定ファイル群を生成プロンプトに連結する際の規則:

- **同一カテゴリ内のファイル間** は単一改行(`\n`)でベタ連結する。
  例: `characters/` に複数ファイルあるとき、リストや段落として連続して並ぶ。
- **異なるカテゴリ間** は空行(`\n\n`)で区切る。
  例: `characters/` ブロックと `worldbuilding/` ブロックの間に 1 行空きが入る。
- システムプロンプト・設定全体・本文 の論理境界は空行(`\n\n`)で区切る。プロンプトテンプレートを使うときは、この区切りの代わりにテンプレートの文字列で包む(本書「プロンプトテンプレート」)。設定全体の中の連結は、テンプレートの有無によらずこの規則のまま。
- ファイル本文の先頭/末尾の空行は trim する。同一カテゴリ内のファイル境目に段落区切りを入れたい場合は、ファイル本文の中間に空行を書くことで実現する。

カテゴリ名やファイル名から自動で見出し(`# キャラ設定: すみれ` のような行)を**プロンプトに付与しない**。Instruct 系の小規模ローカル LLM がプロンプト中の見出しに引きずられて生成側にも同様の見出しを盛ってくる挙動を避けるため、また書き手が「設定ファイルにどう見出しを付けるか」を自分で制御できるようにするため。書き手がファイル冒頭に見出しを書きたければ自分で書く。

### 本文の前処理(ルビ剥がし)

提案要求時に AI に渡す本文からはカクヨム式ルビ記法 `|漢字《かんじ》` を剥がす。Instruct 系の小規模ローカル LLM にルビ記法を含む本文を見せると、生成側もルビ記法を盛ってくる(本来不要な箇所にも `|彼女《かのじょ》` のように付けてくる)ため。

剥がすのは API 送信時のみで、エディタ上の本文表示には影響しない。併せてシステムプロンプトでも「ルビ記法を使わない」ことを指示する(保険)。

## 挿し絵の情景文

本文エディタで選んだ場面から、挿し絵のための日本語の情景文をローカル推論で生成し、メモの末尾に追記する(2026-11-05、`illustration-prompt` spec)。情景文は、書き手が ComfyUI の日本語→英語のプロンプト変換ワークフローに渡す素材で、英訳・タグ・品質の接頭辞・ネガティブプロンプトは作らない。書き手への見え方は `ux.md`「挿し絵の情景文」、範囲の判断と採らなかった案は `roadmap.md`「挿絵生成」を参照。

### 生成経路

続き生成とは別の 2 本目の生成経路だが、アダプタ・`AIProvider` の契約・エンドポイントは変えない。指示文を `systemPrompt`、見出し付きの文脈を `body` に入れ、`contextSections` を空にした `GenerationRequest` を、挿し絵用のプリセット(下)で包んで `OpenAICompatibleAdapter.generateStream`(`llama-server` プロバイダでは、それを継承する `LlamaServerAdapter`)に送る。送り先は続き生成と同じ `/v1/completions` で、Chat API は使わない。

- 挿し絵用のプリセットは、どれもプロンプトをモデルの番の開始で終える。アダプタはプロンプトの続きを返すだけ(本書「役割」の契約のまま)だが、その続きがモデルの応答、つまり情景文になる。
- 生成のライフサイクルは `editor/illustration/illustrationController.ts` が持つ。提案コントローラとは互いに import しない。相手が生成中かどうかは、相手のストア(`useSuggestionStore.generating` / `useIllustrationStore.startedAt`)だけを読む。
- 使えるのは、ローカルの Completion のプロバイダ(OpenAI 互換と `llama-server`。判定は `isLocalCompletionProvider`)だけ。`llama-server` は 2026-11-12 に加えた(`llama-server-provider` spec)。OpenAI プロバイダ(クラウド)の Chat 経路は、system に続き生成の指示を前置きするので、指示に答える形にならない。
- 接続先・モデル・思考の分離の設定(`thinking`)は続き生成と共通。テンプレート・温度・最大トークン・タイムアウト・指示文は、`illustration`(本書「`sumire.json`」節)の値を使う。`topP` と `extras` は、続き生成の `parameters` の値をそのまま送る。
- タイムアウトは、`{ ...config, timeoutMs: 挿し絵用の値 }` の写しで `getProvider` を呼んで効かせる。`getProvider` は設定オブジェクトの参照をキーにキャッシュするので、写しには毎回新しいアダプタができる(アダプタの生成は軽い)。
- 応答は `createThinkingSplitter(resolveThinkingTags(config.thinking))` に流し、`finish()` の結果で終わり方を決める(本書「思考ブロックの分離」の終わり方と同じ手順)。終了理由は、本文が空のチャンクを読み飛ばす前に記録する。ゴーストを出さないので、スナップショットは使わない。
- 生成中も本文に dispatch しない。提案のライフサイクル(暗黙のキャンセル)にも登録しないので、入力・カーソル移動・章の切り替えでは止まらない。止まるのは `Esc`(中止)と、プロジェクトの変更(閉じたときを含む)だけ。開始時のプロジェクトのパスを記録し、`useAppStore` を購読して、パスが変わったら中止する。追記の直前にも、中止されていないことと、プロジェクトが変わっていないことを確かめる。
- 開始時に章ファイル名を記録する。生成中に別の章を開いても、追記するエントリには開始時の章ファイル名を書く。
- 同時に進める生成は 1 つだけ。開始の条件(生成中でないこと、提案の生成中でないこと、プロジェクト、プロバイダ、挿し絵の設定、場面)は、生成中の状態を作る前にすべて確かめる。満たさなければトーストを出して戻り、状態を残さない。`llama-server` プロバイダでは、これらを通ったあと、生成中の状態を作る直前に起動の関門(本書「llama-server プロバイダ」の「起動と停止の時機」)を通す。「場面がコンテキストに収まらない」だけはトークンの計測が要るので、生成中の状態を作ったあとに判定し、状態を戻してから伝える。文言は `ux.md`「挿し絵の情景文」のトーストの一覧。

### 挿し絵用のプリセット

`illustration.template` には、続き生成のテンプレート(本書「プロンプトテンプレート」)と同じ名前の内蔵プリセットと、自由記述を書ける。名前が同じでも中身は挿し絵用の別の表で、定義は `domain/providers/promptTemplate.ts` の `ILLUSTRATION_TEMPLATE_PRESETS`。解決は `resolvePromptTemplate(raw, ILLUSTRATION_TEMPLATE_PRESETS)` で行い、規則(`preset` / `custom`、`{{body}}` が必須、差し込み口の重複は不可)は続き生成と同じ。`resolvePromptTemplate` の第 2 引数を省くと続き生成の表(`PROMPT_TEMPLATE_PRESETS`)を使うので、続き生成の解決は変わらない。

| 名前 | 書式 | 思考 |
| --- | --- | --- |
| `gemma4` | Gemma 4 | 止める(モデルの番の頭に空の思考チャンネルを置く) |
| `gemma4-think` | Gemma 4 | あり(system の番の頭で思考を有効にする) |
| `chatml` | ChatML | 先埋めなし |
| `chatml-nothink` | ChatML | 止める(モデルの番の頭に空の思考ブロックを置く) |

4 つとも、指示文(`{{system}}`)を system の番に、文脈(`{{body}}`)を user の番に置き、プロンプトをモデルの番の開始で終える。`{{settings}}` は置かない。区切りの綴りは続き生成のプリセットと同じ。

各プリセットの中身は次のとおり。コード片の行の切れ目は改行(`\n`)1 つを表す。最後の行の後ろの改行は、`gemma4` は無し(`<channel|>` で終わる)、`gemma4-think` と `chatml` は 1 つ、`chatml-nothink` は 2 つ(`</think>` の後ろに空行が 1 つ入る)。

`gemma4`:

```
<|turn>system
{{system}}<turn|>
<|turn>user
{{body}}<turn|>
<|turn>model
<|channel>thought
<channel|>
```

`gemma4-think`(最後の `<|turn>model` の後ろに改行が 1 つ付く):

```
<|turn>system
<|think|>{{system}}<turn|>
<|turn>user
{{body}}<turn|>
<|turn>model
```

`chatml`(最後の `<|im_start|>assistant` の後ろに改行が 1 つ付く):

```
<|im_start|>system
{{system}}<|im_end|>
<|im_start|>user
{{body}}<|im_end|>
<|im_start|>assistant
```

`chatml-nothink`(最後の `</think>` の後ろに改行が 2 つ付く):

```
<|im_start|>system
{{system}}<|im_end|>
<|im_start|>user
{{body}}<|im_end|>
<|im_start|>assistant
<think>

</think>
```

- 想定する使い方は、思考ありのモデルに `gemma4-think` で場面を整理させること。思考を情景文から分けるには、続き生成と同じく、書き手が `thinking.tags` にそのモデルのタグの組(Gemma 4 なら `{ "open": "<|channel>", "close": "<channel|>" }`)を書いておく。書いていなければ、思考は分離されずに情景文としてメモに入る。続き提案のテンプレートとして AI 設定画面で `gemma4-think` を選んだことがあれば、Gemma 4 の組はそのときに書き足されている(本書「プロンプトテンプレート」)。
- 自由記述のテンプレートも続き生成と同じ規則で受け付ける。ただし挿し絵では、設定を `{{body}}` の中の `【設定】` のブロックに入れる(下の「文脈の形」)ので、`{{settings}}` に入る内容は常に空になる。`{{settings}}` を書いてもエラーにはならないが、何も入らない。`{{system}}` を省くと、指示文はプロンプトに入らず、トークン予算でも数えない。
- `gemma4-think` は 2026-11-05 に実機(text-generation-webui の `gemma-4-31B-it`)で確かめた。3 場面とも思考のあとに情景文が出て、思考は分離できた。`gemma4` / `chatml` / `chatml-nothink` は実機で確かめていない。崩れた場合はプリセットの中身を直す(`sumire.json` の形は変えない)。

### 内蔵の指示文

`illustration.instruction` を書かなければ、次の指示文を `{{system}}` に入れる(`domain/illustration/illustrationConfig.ts` の `DEFAULT_ILLUSTRATION_INSTRUCTION`)。

```text
あなたは小説の挿し絵づくりを手伝うアシスタントです。【挿し絵にする場面】に書かれた場面を、一枚の絵として描くための情景文にまとめてください。【設定】と、場面より前と後の本文は、場面を理解するための材料です。

- 本文の続きを書いたり、本文を書き換えたりしないでください。
- 人物の位置関係・動作・視線・表情・姿勢、場所、時間・天気・光、絵に必要な小道具、構図(視点、距離感、前景と背景)のうち、本文から読み取れるものを書いてください。
- 人物の外見や衣装は、本文か【設定】に書かれているものだけを書いてください。書かれていない外見・衣装・小物・場所の細部を創作してはいけません。
- 心情は、表情・姿勢・視線・手の動き・距離感など、絵で見える形に置き換えて書いてください。
- 出力は日本語の地の文の情景文だけにしてください。見出し、箇条書き、前置き、説明は書かないでください。
```

- 指示文は文脈のブロックを見出しの名前(`【挿し絵にする場面】` など)で指す。差し替えるときも、見出しの名前で指せる。
- 外見を創作させないのは、書き手が外見を ComfyUI 側でタグとして手打ちしているため。情景文に本文に無い外見が入ると、手打ちのタグと食い違う。
- 続き生成のシステムプロンプト(`systemPrompt`)は、挿し絵では使わない。

### 文脈の形

場面・前後の本文・設定を、見出し付きの 1 本の `body` にまとめる(`domain/illustration/illustrationContext.ts` の `buildIllustrationContext`。見出しは同ファイルの `ILLUSTRATION_BLOCK_LABELS`)。

```text
【設定】
{設定ファイルをつないだもの}

【場面より前の本文】
{前の本文}

【挿し絵にする場面】
{場面}

【場面より後の本文】
{後の本文}
```

- 各ブロックは `見出し\n内容`。ブロックの間は `\n\n`。並び順は上のとおりで固定。
- 内容が空のブロック(設定が 0 件、前・後の本文が無い、削った結果が空)は、見出しごと出さない。場面のブロックは必ず出す。
- 設定は、続き生成と同じく「プロンプトに含める」(`includeInContext: true`)のファイルを使う。ファイルの間は本書「プロンプト直列化の改行ルール」の規則でつなぐ(`joinSections`)。ファイル名やカテゴリ名からの見出しは付けない。
- **続き生成の方針の例外**: 続き生成では、Sumire がプロンプトに見出しやラベルを付けない(本書「コンテキストセクションのラベル取り扱い」「プロンプト直列化の改行ルール」)。挿し絵ではこの 4 つの見出しを付ける。指示に答えるタスクでは、絵にする場面と、理解のための材料との境目をはっきりさせる必要があり、指示文から見出しの名前で指せるようにするため。例外はこの経路に限り、続き生成のプロンプトは変えない。
- 本文を読むのは、今の章ファイルの中だけ。前の章は読まない(本書「章境界の扱い」と同じ)。

**場面と前後の本文の取り出し**(`editor/illustration/sceneSelection.ts` の `extractScene`):
- 選択範囲があれば、それを場面にする。無ければ、カーソルのある行を場面にする。日本語 Web 小説では 1 行が 1 段落になる書き方が主なので、「カーソル位置の段落」をカーソルのある行とする。
- 本文の範囲は、フロントマターの後ろから文書の末尾まで。場面がまるごとフロントマターの中(閉じの `---` の行を含む)にあれば、場面なしとする。場面がフロントマターにかかるときは、本文の開始位置から切る。
- 前の本文は、本文の開始位置から場面の手前まで。後の本文は、場面の後ろから文書の末尾まで。
- 場面・前・後のそれぞれからルビを剥がす(本書「本文の前処理(ルビ剥がし)」)。
- 前の本文の先頭と末尾の連続する改行、後の本文の先頭の連続する改行を剥がす(ブロック間の区切りを `\n\n` にそろえるため)。改行以外の空白(行頭の全角空白の字下げなど)は残す。
- 場面が空白だけ(全角空白を含む)なら、場面なしとする。
- 場面の冒頭(メモのエントリの出所の行に使う)は、改行と空白の連続を半角空白 1 つにし、前後の空白を除いた先頭 20 文字。20 文字を超えたら末尾に `…` を付ける。

### 予算配分

前の本文を厚く、後の本文を薄く入れる。窓に収まらなければ、場面から遠い本文から削り、場面そのものは削らない。

1. `W = contextWindow ?? 2048`。`R0 = W − 指示文 − テンプレートの文字列 − 設定ブロック − 場面ブロック − 前後の見出しの分 − maxTokens`(`maxTokens` は挿し絵用の値)。
2. 設定は、続き生成と同じく `settingsTokenBudget`(既定 500)を上限に、ファイル単位で挿入順に詰める(`packSettingSections`)。予算に入らず外したファイルの表示名を記録する。
3. `R0 < 0` なら、採用した設定ファイルを挿入順の後ろから 1 件ずつ外し、そのたびに `R0` を計算し直す。設定が 0 件になっても `R0 < 0` なら、「場面がコンテキストに収まらない」として送らない。設定の分であふれただけのときに、場面が長すぎると伝えないため。
4. 後の本文: `min(後の本文の全量のトークン数, floor(R0 / 4))` を予算に、末尾から削る(`trimBodyTail`)。
5. 前の本文: `R0 − 実際に入れた後の本文のトークン数` を予算に、先頭から削る(`trimBodyHead`)。

- 指示文は、テンプレートに `{{system}}` があるときだけ数える。テンプレートの文字列は、続き生成と同じく差し込み口以外の文字列をつないで数える。
- 前後の見出しは、本文がある側だけ数える。そのため、場面そのものは入るのに前後の見出しの分(数十トークン)だけ足りないときも、「場面がコンテキストに収まらない」になる。最大トークン(既定 4096)に比べて小さいので、このずれは許容する。
- 後の本文は残りの 1/4 までなので、前後とも十分に長ければ、前と後はおよそ 3 : 1 以上になる。前の本文が短くても、後の本文は 1/4 を超えて伸ばさない。
- 外した設定ファイルの表示名は、予算で外したもの(挿入順)、窓からあふれて外したもの(外した順)の順に並べ、送信の前に 1 回だけトーストで伝える。
- 計測は `measureSectionCached`(見出し・テンプレートの文字列・設定・指示文はキャッシュ)と、プロバイダの `countTokens` を使う。本文の切り詰めは続き生成と同じ文字単位の二分探索。ブロック間の `\n\n` を数えないことと、境目のトークン化による 1〜2 トークンのずれは、続き生成と同じく許容する。

### 終わり方とエラーの文言

`finish()` の結果と、最後に受け取った終了理由から、次の順で終わり方を決める。トーストの文言は `ux.md`「挿し絵の情景文」のトーストの一覧。

1. 思考が終わっていない → 終了理由が `length` なら「思考の途中で上限」、それ以外なら「思考が終わらないまま」。追記しない。空より先に見るのは、思考の前の本文が無い応答で「空」と伝えると、最大トークンの見直しに気づけないため。
2. 思考を除いた本文が空(`trim()` で空) → 追記しない。
3. 終了理由が `length` → 途中までの情景文を、途切れた旨の注記つきで追記する。
4. それ以外 → 追記する。

- 中止(`Esc`、プロジェクトの変更)は、追記もトーストもしない。中止のあとに届いた例外も、失敗として伝えない。
- 送信や受信の失敗は、追記しない。途中まで受け取った本文も捨てる。自動で再試行はしない。どの終わり方でも、購読を解いて生成中の状態を戻すので、書き手はもう一度 `Alt+I` を押せる。
- **プロバイダのエラーの文言は続き生成と共有する**(`domain/providers/errorMessage.ts` の `describeProviderError`)。分類と文言は、続き生成の提案コントローラが持っていたものをそのまま移した。`network` / `timeout` / `http` / `parse` / `config` に文言があり、`auth` / `rateLimit` は文言なし(`null`)。
  - 文言は日本語の直書きのままで、i18n を通さない。英語表示でも、この文言だけは日本語で出る。i18n 化は、続き生成と合わせて磨き込みで行う。「プロジェクトを開いてください」も、続き生成と同じく直書き。
  - `null` の扱いは呼び出し側が決める。続き生成は、導入前と同じく `null` ならトーストを出さない(`auth` / `rateLimit` はクラウドの OpenAI アダプタが投げるが、続き生成はこれまでも黙って戻っていた。挙動を変えない)。`ProviderError` でない例外は、これまでどおり「提案要求に失敗しました: …」。
  - 情景文は、`null` のときも `ProviderError` でない例外のときも、「情景文の生成に失敗しました: {{message}}」(`toast.illustrationFailed`)を出す。
- 本 spec のトーストとステータスの文言は `ja.json` / `en.json` に置く(`toast.illustration*`、`toast.suggestionIllustrationBusy`、`status.illustrationGenerating`)。

### メモへの追記

情景文は `appendToMemo` でメモの末尾に追記する。区切りと日時は `Alt+M` の転記と同じ `formatMemoEntry` が付ける(本書「`memo.md`」節)。`appendToMemo` に渡すテキストは `domain/illustration/illustrationEntry.ts` の `formatIllustrationEntry` が作る。

- 1 行目は出所の行で、`〔挿し絵〕{章ファイル名}「{場面の冒頭}」`。章ファイル名は生成を始めたときの章(拡張子つき)。
- 2 行目以降は、前後の空白(全角空白を含む)を除いた情景文。思考は含めない。
- 生成の上限で途切れたときは、空行を挟まずに、末尾に `(生成の上限に達したため、ここで途切れています)` の行を足す。
- 出所の行と注記の文言は、i18n を通さず固定にする。メモに残る本文は、表示言語で変わらないほうがよいため(`formatMemoEntry` の日時と同じ扱い)。
- 情景文が空のときは整形を呼ばない(整形は空でも出所の行を返すため)。

### dev 操作ログ

開発ビルドの dev 操作ログ(`emitDevEvent`)に、`illustration.start`(開始)、`illustration.end`(失敗以外の終わり)、`illustration.error`(失敗)を出す。

- `illustration.start` の payload は、テンプレートの出典(`template`。プリセットなら名前、自由記述なら `custom`)だけ。
- `illustration.end` / `illustration.error` の payload は、`template`、所要ミリ秒(`durationMs`)、最後の終了理由(`finishReason`)、終わり方の種類(`outcome`)と、文字数の内訳(受け取った応答の総文字数 `responseChars`、思考を除いた情景文の文字数 `textChars`、その差 `thinkingChars`)。失敗のときはエラーの分類(`errorKind`)を足す。
- 文字数は UTF-16 の単位。トークン数はストリーミングの応答に含まれないので、思考の長さの目安として文字数で代える。`thinkingChars` には、思考ブロック(タグを含む)のほかに、つなぎで除いた改行なども入る。思考の分離を終える前に終わったとき(送信しなかった、受信中の失敗・中止)は、`textChars` と `thinkingChars` は `null`。
- 本文・場面・情景文・思考・指示文・エラーの本文は入れない。

### 採らなかった実装の案

| 案 | 採らない理由 | 再検討の条件 |
|---|---|---|
| `AIProvider` に指示に答えるためのメソッドを足す | ローカルの OpenAI 互換だけを対象にする今は、実装が 1 つで間接層が要らない。プリセット表の引数 1 つで、テンプレートの解決・描画・計測をそのまま共有できる | クラウド対応を始めるとき(Chat 経路の内蔵の指示との関係を見直す) |
| `/v1/chat/completions` で送り、テンプレートをサーバーに任せる | 続き生成で採らないと決めた経路(本書「Chat ではなく Completion を使う」)。思考の返し方がサーバーごとに違う | クラウド対応を始めるとき |
| 設定を `{{settings}}` に入れる(見出しなし) | 見出しで境目がはっきりし、指示文から見出しの名前で指せる(書き手と合意、2026-11-05) | 見出しにモデルが引きずられ、情景文に見出しや箇条書きを書くようになったとき |
| テンプレートが無いとき、素の連結で送る | 指示チューニングのモデルでは崩れた出力が出て、原因が分からない(本書「プロンプトテンプレート」と同じ理由)。テンプレートを必須にし、無ければトーストで伝えて送らない | テンプレート無しでも指示に答えるモデルを主に使うようになったとき |

## llama-server プロバイダ

Sumire が `llama-server`(llama.cpp の推論サーバー)を子プロセスとして起動・停止するプロバイダ(2026-11-12、`llama-server-provider` spec)。プロバイダ ID は `llama-server`、画面での名前は「llama.cpp(Sumire が起動)」。書き手は左ペインでモデル(量子化)を選ぶだけで、Sumire がそのモデルを決めてあるコンテキスト長で読み込み、同じ値でプロンプトの予算を計算する。書き手への見え方は `ux.md`「左下: LLM 切り替えペイン」「llama-server プロバイダの動線」「AI 接続設定 UI」、管理の主体を改めた経緯は本書「推論サーバーの管理」を参照。

- 推論は独立プロセスのままで、Sumire は HTTP で話す。生成の経路(`/v1/completions`、SSE の解釈、テンプレート、思考の分離、挿し絵の情景文)は OpenAI 互換プロバイダと同じコードを通る(本書「MVP で実装するアダプタ」の `LlamaServerAdapter`)。
- `llama-server` の実行ファイルとモデルは同梱しない。書き手が自分の GPU に合ったものを用意し、パスを指す(`roadmap.md`「採らない方針」)。
- 動作を確かめているのは Windows と、作者が使う `gemma-4-31B-it` の gguf だけ。ほかの gguf も一覧に並び、選べば起動するが、確かめていない。
- 役割の分担: プロセスの生死と状態は Rust(`commands/llama_server.rs`)、設定と「いつ起動し、いつ止めるか」はフロントの `stores/llamaServerStore.ts`、生成は既存のアダプタの経路。コントローラは起動の関門の関数を 1 つ呼ぶだけ。

### 設定の置き場所

PC に固有の値(実行ファイルのパス、モデルのフォルダ、モデルごとのコンテキスト長、いま使うモデル、追加の起動引数)は、アプリデータディレクトリの `preferences.json`(本書「アプリデータディレクトリ」)に置く。どのプロジェクトを開いても同じ設定を使う。`sumire.json` には書かない。

```json
{
  "llamaServer": {
    "executablePath": "C:\\text-generation-webui_v4.x\\installer_files\\env\\Lib\\site-packages\\llama_cpp_binaries\\bin\\llama-server.exe",
    "modelsDir": "C:\\text-generation-webui_v4.x\\user_data\\models",
    "extraArgs": ["--flash-attn", "on"],
    "selectedModel": "gemma-4-31B-it.Q3_K_M.gguf",
    "models": {
      "gemma-4-31B-it.Q3_K_M.gguf": { "contextSize": 131072 },
      "gemma-4-31B-it.Q5_K_M.gguf": { "contextSize": 81920 }
    }
  }
}
```

| キー | 未設定の値 | 意味 |
| --- | --- | --- |
| `executablePath` | `""` | `llama-server` の実行ファイルのパス |
| `modelsDir` | `""` | モデルのフォルダ。直下の gguf がモデルの一覧になる |
| `extraArgs` | `[]` | 追加の起動引数。1 要素が 1 引数。全モデル共通 |
| `selectedModel` | `null` | いま使うモデルのファイル名 |
| `models` | `{}` | モデルごとの設定。キーはファイル名で、値は `{ "contextSize": 正の整数 }` |

- 読み書きは Rust の `read_app_preferences` / `write_app_preferences` が文字列のまま行い、解析と書き戻しはフロントの `domain/llamaServer/preferences.ts` が行う。書き込みは、一時ファイルに書いてから置き換える。
- ファイルが無い・JSON として壊れている・オブジェクトでないときは、すべて未設定として動く。`llamaServer` の中で型の合わない部分は、その部分だけ未設定の値にする。`contextSize` は 1 以上 4294967295 以下の整数だけを採る(Rust 側が起動の要求のコンテキスト長を `u32` で受けるため。上限の定数は `preferences.ts` の `MAX_CONTEXT_SIZE` で、AI 設定画面の入力の検証も同じ値を使う)。範囲の外のエントリは捨てる。
- 書き戻すときは、読んだ JSON の `llamaServer` 以外のトップレベルのキーを保つ。
- `models` のエントリは、ファイルがフォルダから無くなっても消さない(戻したときに値が残る)。モデルの一覧を読み直しても消さない。
- モデルの一覧は、Rust の `list_gguf_models` が `modelsDir` の直下から作る。拡張子が `.gguf`(大文字小文字を区別しない)のファイルだけを、大文字小文字を無視したファイル名の昇順で返す。下の階層は見ない。gemma4 以外の gguf も並び、Sumire は絞り込まない。フォルダが無い・読めないときは、一覧を空にして、読めないことを AI 設定画面と左ペインに出す。
- フロントが持つ一覧は、最後に読んだときのもの。読み直すのは次の時機: アプリの起動時、モデルのフォルダの指定を変えたとき、AI 設定画面の「一覧を読み直す」、左ペインの `llama-server` の行を展開したとき(展開された状態で表示されたときを含む)、起動の直前(下の「起動と停止の時機」)。フォルダの変化を見張ることはしない。
- 設定(パス・追加の起動引数・動いているモデルのコンテキスト長)を変えても、動いている `llama-server` は起動し直さない。次の起動から効く。
- 入力は AI 設定画面と左ペインから行う(`ux.md`)。

作品ごとの設定は、ほかのプロバイダと同じく `sumire.json` の `aiConfig.providers["llama-server"]` に持つ(本書「`sumire.json`」節の「`llama-server` のセクション」)。

**`sumire.json` に置かないものと、その理由**:
- 接続先・モデル・コンテキスト長は PC に固有で、プロジェクトは別の PC に持ち運べるため。
- 実行ファイルのパスと起動引数は、安全のためにも `sumire.json` に置かない。`sumire.json` は持ち運ぶ・受け取ることがあるファイルなので、そこに実行ファイルのパスや引数を置くと、受け取ったプロジェクトから任意のプログラムが実行されうる。実行するのは、書き手がアプリ側の設定で指した実行ファイルだけにする。プロジェクトを開いただけで、任意のプログラムが実行されることはない。

### 起動引数

`commands/llama_server.rs` の `build_args` が、次の並びで組み立てる。

```
--model <モデルの絶対パス> --ctx-size <コンテキスト長> --host 127.0.0.1 --port <ポート> --parallel 1 <追加の起動引数…>
```

- 固定で渡すのは 5 組(`--model`、`--ctx-size`、`--host`、`--port`、`--parallel`)だけ。そのあとに、`extraArgs` をそのままの順で足す。
- `--ctx-size` は必ず明示する。省くと、モデルの学習時の長さ(`gemma-4-31B-it` では 262144)を上限に自動で決まり(作者の環境では 168,960 になった)、GPU メモリからあふれる。コンテキスト長が 1 未満の起動の要求は、command がエラーを返して起動しない。
- `--host 127.0.0.1` で、同じ PC の中からだけ接続できる形にする。
- `--parallel 1` は、スロットが複数になってコンテキスト長が分割されるのを防ぐ。
- `--fit` は渡さず、`llama-server` の既定(`on`)に任せる。`--ctx-size` を明示すれば、`--fit` がコンテキスト長を書き換えることは無い(下の「根拠」)。`--fit` の有無で変わるのは、収まらないときの遅くなり方だけで、どちらも失敗にはならない。text-generation-webui が渡している `--fit-target 512` は、GPU メモリの空きを 512 MiB しか残さず、後からほかのアプリが GPU を使うとあふれる原因になっていた。`llama-server` の既定(1024 MiB)のほうが安全なので、Sumire からは指定しない。
- 引数名はビルドによって変わりうる(`--no-webui` は非推奨の別名になっている)。Sumire が固定で渡す引数は、昔からあって意味が変わりにくいものに絞り、ほかは書き手が追加の起動引数に書く。
- Web UI を止める引数も渡さないので、`llama-server` の Web UI が `127.0.0.1` の空きポートで開いたままになる。同じ PC の中からしか届かないので許容する。止めたければ追加の起動引数に書ける。
- 追加の起動引数に `--host` を書けば、書き手の責任で待ち受けを変えられる。その場合も、Sumire は `127.0.0.1` に送り続ける。
- 引数は配列のまま渡し、シェルを通さない。Windows では、コンソールのウィンドウを出さずに起動する(`CREATE_NO_WINDOW`)。

### ポートの決め方

起動のたびに、`127.0.0.1:0` に待ち受けを作って空きポートの番号を得て、待ち受けを閉じてから `--port` に渡す。書き手に接続先を設定させない。

- text-generation-webui(5000 / 5005 番)や、ほかの `llama-server`(既定の 8080 番)と衝突しない。
- フロントは、Rust から届く状態(`port`)で接続先を知る。接続先は `http://127.0.0.1:<port>/v1`。
- 待ち受けを閉じてから `llama-server` が待ち受けるまでの間に、ほかのプロセスが同じポートを取ることが理屈の上ではある。その場合は `llama-server` が終了し、読み込みの失敗として伝わる。書き手がもう一度要求すれば、別のポートで起動する。

### 状態

状態は Rust 側の監督(`Supervisor` と `StatusMachine`)が持ち、フロントの `llamaServerStore` はそれを写す。

| 状態(`state`) | 意味 | 持つ値 |
| --- | --- | --- |
| `stopped`(停止中) | 動いていない | `cause`: `initial`(一度も起動していない) / `requested`(停止の操作) / `exited`(準備完了のあとにプロセスが終了した)、`exitCode` |
| `loading`(読み込み中) | 起動して、準備完了を待っている | `modelPath`、`contextSize`、`port` |
| `ready`(準備完了) | 生成を受け付けられる | `modelPath`、`contextSize`、`port` |
| `failed`(失敗) | 起動できなかった、または読み込みの途中で終了した | `reason`: `spawn`(起動できない) / `exited`(途中で終了)、`executablePath`、`modelPath`、`message`、`exitCode` |

どの状態も、起動の通し番号 `runId` を持つ。フィールド名は camelCase で、`state` で判別する(TypeScript の型は `domain/llamaServer/types.ts` の `LlamaServerStatus`)。

```
stopped / failed ──start──▶ loading ──/health が 200──▶ ready
loading ──起動できない・途中で終了──▶ failed
loading / ready ──stop──▶ stopped(requested)
ready ──プロセスの終了──▶ stopped(exited)
loading / ready ──start(別のモデル)──▶ loading
```

- **同時に動かすのは 1 つ**: 起動は、動いているプロセスがあれば先に強制終了して、終了を待ってから行う。
- **通し番号**: `runId` は、起動のたびと、動いているものを停止するたびに進む。準備完了の待ちと終了の見張りは、自分が始まったときの `runId` が今のものと同じときだけ状態を書き換える。止めたプロセスや置き換えられたプロセスの知らせで、状態が書き換わらないようにするため。
- **準備完了の待ち**: 0.5 秒おきに `GET http://127.0.0.1:<port>/health` を呼び、ステータスが 200 なら `ready` にして待ちを終える。接続の失敗と 200 以外(読み込み中は 503)は「まだ」として扱う。1 回の要求は 5 秒で区切るが、待ち全体に時間切れは設けない(書き手が停止で取りやめられる)。`ready` のあとは HTTP を送らない。
- **終了の見張り**: 0.25 秒おきにプロセスの終了を確かめる(`try_wait`)。HTTP の通信ではないので、「常時 ping はしない」(本書「接続喪失時の挙動」)には当たらない。`loading` の間に終了したら `failed`(`exited`)、`ready` のあとに終了したら、失敗ではなく `stopped`(`exited`)にする。
- **停止**: 強制終了(`Child::kill`)して、終了を待つ。強制終了で GPU メモリは 2 秒以内に空くので(下の「根拠」)、穏やかな終了の手順は持たない。動いていなければ何も変えずに今の状態を返す(冪等)。
- **出力の末尾**: 標準出力と標準エラーを、それぞれ専用のスレッドで読み続ける(読まないと `llama-server` が出力で止まる)。末尾 200 行だけをメモリに持ち、超えたら古い行から捨てる。起動のたびに空にする。ファイルやログには書かない。失敗の手がかり(`llama-server` は原因を標準エラーの末尾に出す)として、AI 設定画面の「サーバーの出力」で見られる。
- **呼び出し元を止めない**: 待ちと見張りは別スレッドで動く。起動と停止の command は、強制終了と終了の待ちの間スレッドを止めるので、`async` の command から `tauri::async_runtime::spawn_blocking` で呼ぶ。読み込み中も、本文の編集・保存・メモ・設定の操作は妨げない。

**command とイベント**:

```typescript
interface StartLlamaServerRequest {
  executablePath: string;
  modelPath: string;       // 絶対パス
  contextSize: number;     // 正の整数
  extraArgs: string[];
}

// invoke("start_llama_server", { req }) : LlamaServerStatus   // loading か failed(spawn)
// invoke("stop_llama_server") : LlamaServerStatus             // stopped(requested)。動いていなければ今の状態
// invoke("read_llama_server_status") : LlamaServerStatus
// invoke("read_llama_server_log") : string[]                  // 出力の末尾(古い順)
// invoke("read_app_preferences") : string | null              // preferences.json の中身。無ければ null
// invoke("write_app_preferences", { json }) : void
// invoke("list_gguf_models", { dir }) : { fileName: string; sizeBytes: number }[]
```

- 状態が変わるたびに、Rust がイベント `llama-server-status`(payload は `LlamaServerStatus`)を全ウィンドウに送る。フロントのラッパーは `domain/llamaServer/llamaServerApi.ts`。
- フロントの状態の受け口は 1 つ(`llamaServerStore` の `applyStatus`)で、イベントも、起動・停止の command の戻り値もここに通す。手元より古い `runId` の知らせは捨てる。同じ `runId` の中では前にしか進めない(`loading` → `ready` / `failed` / `stopped`、`ready` → `stopped`)。同じ知らせが command の戻り値とイベントの両方で届いても、トーストは 1 回になる。
- フロントは、起動・停止の command を呼ぶ前に、ストアの状態を先に書き換える(起動なら仮の `loading`、停止なら `stopped`)。生成中のコントローラが、プロセスが止まる前に生成を中止できるようにするため(下の「起動と停止の時機」)。仮の `loading` は `runId` を手元の値のまま、`port` を 0 にする。本物の状態は `runId` が進んでいるので、届いたときに受け口が採る。

### 起動と停止の時機

`llama-server` を起動するのは、提案か情景文を要求したときと、動いている間に別のモデルを選んだときだけ。読むだけ・直すだけの日は GPU を使わない。

| 出来事 | 起こること |
| --- | --- |
| アプリの起動、プロジェクトを開く | 起動しない。アプリの起動時に、設定を読み、モデルの一覧を作り、Rust 側の今の状態を写すだけ(`initLlamaServerStore`) |
| 「現在使うプロバイダ」を `llama-server` にする | 起動しない。選択を `sumire.json` に保存するだけ |
| 止まっているとき(`stopped` / `failed`)の提案・情景文の要求 | 設定を検査し、通れば読み込みを始める。その要求では生成しない。読み込みを始めたことをトーストで知らせる |
| 読み込み中(`loading`)の要求 | 生成しない。読み込み中であることをトーストで知らせる。待ってから生成はしない |
| 準備完了(`ready`)の要求 | 待たせずに生成する |
| 準備完了になった | トーストで知らせる。書き手が要求し直す |
| モデルを選ぶ(止まっているとき) | 選択を保存するだけ。次の要求で読み込む |
| 別のモデルを選ぶ(`loading` / `ready` のとき) | 動いているものを止め、選んだモデルの読み込みを始める。読み込みを始めたことを、最初の要求のときと同じトーストで知らせる。検査に当たれば(起動の直前の読み直しで、選んだモデルがフォルダに無いと分かったときを含む)、そのトーストを出して止めるだけにする |
| 「現在使うプロバイダ」をほかに切り替える | `loading` / `ready` なら止める |
| プロジェクトを閉じる | `loading` / `ready` なら止める |
| 左ペインの「停止」 | 止める(読み込み中なら、読み込みを取りやめる) |
| Sumire の終了 | 止める(下の「後始末」) |
| 準備完了のあとに `llama-server` が終了した | `stopped`(`exited`)にしてトーストで知らせる。自動では起動し直さない。次の要求で、止まっているときと同じく読み込みを始める |

**起動の関門**(`llamaServerStore` の `prepareLlamaServerConfig`): 提案コントローラと挿し絵コントローラが、ほかの開始条件(テンプレートの不備、挿し絵の設定、場面なし)をすべて通ったあと、生成中の状態を作る直前に呼ぶ同期の関数。送れない要求で数十秒の読み込みを始めないために、最後に置く。

- `llama-server` 以外の設定は、同じ参照のまま通す。OpenAI 互換・OpenAI プロバイダの挙動は変わらない。
- `ready` なら、実効の `AIConfig`(下の「コンテキスト長の扱い」)を返す。設定の参照・`runId`・実際のコンテキスト長が同じ間は、同じ参照を返す(`getProvider` が設定の参照でアダプタをキャッシュするため)。
- `loading` なら、トーストを出して断る。
- `stopped` / `failed` なら、次の順で検査し、当たったらそのトーストを出して断る(起動しない): 実行ファイルのパスが未設定 → モデルが未選択 → 選んだモデルが一覧に無い → そのモデルのコンテキスト長が未設定。すべて通れば、状態を先に仮の `loading` に書き換えて断り、続きの起動の手順(下の「起動の直前の一覧の読み直し」)は待たない。
- 断られたコントローラは、ゴーストも生成中の表示も出さずに戻る。
- コンテキスト長が未設定のモデルを、自動の値や既定値で起動することはしない。

**起動の直前の一覧の読み直し**: 関門からの起動も、モデルの選び直しによる起動し直しも、仮の `loading` に書き換えたあと、`start_llama_server` を呼ぶ前に `list_gguf_models` でフォルダの今の中身を読み、ストアの一覧を作り直す。関門の検査が見る一覧は最後に読んだときのもので、そのあとで消えた・改名された gguf を通してしまうため。

- 選んだモデルが今の一覧にあれば、読み込みを始めたトーストを出し、`start_llama_server` を呼ぶ。トーストをここで出すのは、無いと分かったときにトーストが 2 つ続かないようにするため。関門が戻った時点では、まだ出ていない。
- 選んだモデルが無ければ、起動せず、「モデルのフォルダにありません」のトーストを出して、仮の `loading` を取り消す。関門からの起動なら、元の状態(`stopped` / `failed`)に戻す。起動し直しなら、動いていたものを止めて `stopped`(`requested`)にする(生成中のコントローラは、仮の `loading` に書き換えた時点でもう中止させているため、`ready` には戻さない)。
- フォルダを読めなければ、同じく起動せずに取り消し、一覧を空にして読めないことを持ち、「モデルのフォルダを読めません」のトーストを出す。
- 読んでいる間に、あとから止められた・別の起動が始まったときは、何もせずに終える。判定は、起動の手順の世代番号(新しい起動を始めるたびと、停止のたびに進める)で行う。先行の command の結果(停止の戻り、前の起動の戻り)が届いて仮の `loading` を上書きしただけなら、取りやめない。届いた通し番号で仮の `loading` を書き直してから起動する(取り消すときの戻し先も、届いた状態から決め直す)。
- `start_llama_server` そのものが失敗した(command を呼べない)ときも、仮の `loading` を同じ先に戻し、起動できないトーストを出す。

**生成中の停止と切り替え**: コントローラは、`llama-server` で生成している間 `llamaServerStore` を購読し、状態が `ready` でなくなるか `runId` が変わったら、生成を中止する(提案は既存の停止と同じ経路、挿し絵は中止と同じ経路)。停止・モデルの切り替えの前にストアの状態を先に書き換えるので、生成が中止されてから、プロセスが止まる。中止なので、失敗のトーストは出ない。`llama-server` が自分で落ちたとき(書き手の操作でない終了)は、生成の失敗のトーストと、終了のトーストの両方が出ることがある。許容する。

書き手が生成を中止する(`Esc`、暗黙のキャンセル)ときは、HTTP の接続を切って `llama-server` での生成を止めるだけで(本書「ストリーミング生成」)、`llama-server` 自体は止めない。

### 状態の伝え方

- **イベント**: 上の `llama-server-status`。フロントはストアに写し、左ペインの状態の 1 行(停止中 / 読み込み中 / 準備完了 / 失敗)に出す。
- **トースト**: 読み込みの開始、読み込み中の要求、準備完了、設定の不足(4 種)、起動できない、読み込みの失敗、準備完了のあとの終了、コンテキスト長の食い違い、設定の保存の失敗。場面と文言は `ux.md`「llama-server のトーストの一覧」。書き手の操作での停止(`stopped` の `requested`)では出さない。
- **出力の末尾**: 失敗の原因は、AI 設定画面の「サーバーの出力」で確かめる。読み込みの失敗のトーストが、そこを見るよう案内する。
- 生成そのものの失敗(接続・タイムアウト・HTTP)は、OpenAI 互換プロバイダと同じ文言(`describeProviderError`)。
- どの失敗でも、本文の編集・保存は続けられる。自動の再試行・再起動はしない。

### コンテキスト長の扱い

コンテキスト長はモデル(量子化)ごとに 1 か所(`preferences.json` の `models.<ファイル名>.contextSize`)で決め、起動(`--ctx-size`)とプロンプトの予算計算の両方に使う。量子化ごとに、GPU に収まるコンテキスト長が違うため(作者の環境では Q3_K_M で 131072、Q5_K_M で 81920)。

- **実効の `AIConfig`**(`domain/llamaServer/effectiveConfig.ts` の `buildEffectiveConfig`): `sumire.json` の `llama-server` のセクションに、`endpoint`(`http://127.0.0.1:<port>/v1`)、`model`(モデルのファイル名)、`contextWindow` を埋めたもの。ほかの項目(生成パラメータ、テンプレート、思考の分離、挿し絵の設定など)はセクションのまま。ContextBuilder と挿し絵の予算配分は `AIConfig.contextWindow` と `countTokens` しか見ないので、この設定を渡せば変更が要らない。実効の値は保存しない(`aiConfigStore` にも `sumire.json` にも入れない)。
- `sumire.json` のセクションに `contextWindow` が書かれていても使わない。AI 設定画面にも、その欄を出さない。
- **`/props` で確かめる**: 準備完了になったら、フロントが `GET /props` を読み、`default_generation_settings.n_ctx`(実際に確保されたコンテキスト長)を持つ。指定した値と違えば、食い違いをトーストで知らせ、予算には実際の値を使う。`/props` を読めない(5 秒で区切る)・値が正の整数でないときは、指定した値をそのまま使い、食い違いのトーストは出さない。
- モデルを切り替えると `runId` が変わるので、切り替えたあとの生成から、新しいモデルのコンテキスト長で予算を計算する。
- **Sumire は値を変えない**: 書き手が指定したコンテキスト長を、自動で別の値にして起動することはしない。GPU メモリからの逆算もしない。
- **収まらない値は、実測では失敗ではなく速度の低下として現れた**: GPU メモリに収まらないコンテキスト長を指定しても、実測では読み込みは失敗しなかった。`--fit` が GPU に載せる層を減らして CPU に回すか、GPU メモリがほぼ満杯になって、生成が遅くなった(下の「根拠」)。Sumire はこの速度の低下を検出しない。メモリが足りずに読み込み自体が失敗したときは、読み込みの失敗として伝わる(本書「状態の伝え方」)。コンテキスト長は、書き手が自分の GPU に収まる値を決める。ほかのアプリが同じ GPU を使っているかどうかも、Sumire は関知しない。

### 後始末

Sumire が起動した `llama-server` は、Sumire がどう終わっても残さない(残ると GPU メモリを掴んだままになる)。

- **通常の終了**: `lib.rs` が `RunEvent::Exit` で停止(強制終了と終了の待ち)を呼ぶ。終了の途中なので、状態は誰にも送らない。
- **異常終了・強制終了**(Windows): アプリの起動時に、「ハンドルが閉じたら中のプロセスを終了させる」(`KILL_ON_JOB_CLOSE`)ジョブオブジェクトを 1 つ作って持ち続け、起動した子プロセスを、起動の直後にそのジョブへ割り当てる(`win32job` crate)。Sumire のプロセスがどんな終わり方をしても、ジョブのハンドルが閉じた時点で、OS が `llama-server` を終了させる。Sumire の側の終了処理は強制終了では走らないので、OS に任せる。
- `llama-server` は子プロセスを作らないので、起動から割り当てまでの間に、ジョブの外へ孫プロセスが漏れることは無い。将来、子プロセスを作るビルドに変わると、強制終了だけでは孫が残るが、その場合もジョブオブジェクトが後始末する。
- ジョブを作れない・割り当てられないときは、標準エラーに出すだけにして、起動は続ける(Rust 側に動作ログの仕組みが無いため。リリースビルドでは残らない)。その場合、残さない手立ては通常の終了時の停止だけになる。
- Windows 以外では、通常の終了時に止めるだけ(Windows 以外は動作を確かめていない)。
- 複数の Sumire を同時に起動したときの調停はしない。

### トークン数の計測

`LlamaServerAdapter.countTokens` は、接続先の末尾の `/v1` を除いた先の `POST /tokenize` に `{ "content": 本文 }` を送り、返ってきた `tokens` の配列の長さを返す。読み込んだモデルのトークナイザで数えるので、プロンプトテンプレートの区切り(`<|turn>` など)も、モデルが 1 トークンとして扱うとおりに数えられる。

- 失敗したとき・`tokens` が配列でないときは、OpenAI 互換アダプタと同じ文字数からの推定に落とす。
- text-generation-webui 固有の `/v1/internal/token-count` には頼らない。
- **トークン数のキャッシュを消す時機**: ContextBuilder のトークン数のキャッシュ(`contextBuilder.ts` の `sectionTokenCache`。設定ファイルやテンプレートの文字列の計測値を持ち、挿し絵の予算配分も同じものを使う)は、キーが文字列だけで、プロバイダもモデルも区別しない。別のトークナイザで数えた値や、`/tokenize` が使えない間の推定値を持ち越さないよう、`llamaServerStore` が次の時機に `clearContextBuilderCache()` を呼ぶ。
  - `llama-server` が準備完了になったとき(起動のたび。モデルの切り替えを含む)。ここから `/tokenize` で数えられる。
  - 「現在使うプロバイダ」が変わったとき(どのプロバイダからどのプロバイダへでも。プロジェクトを開く・閉じるときを含む)。
  - 同じプロバイダのまま、OpenAI 互換の接続先やモデル名を変えたときは消さない(`polish-backlog.md`)。

### llama-server の dev 操作ログ

開発ビルドの dev 操作ログ(`emitDevEvent`)に、次を出す。

| イベント | payload |
| --- | --- |
| `llamaServer.start` | モデルのファイル名(`model`)、コンテキスト長(`contextSize`) |
| `llamaServer.ready` | 読み込みのミリ秒(`durationMs`)、実際のコンテキスト長(`actualContextSize`。読めなければ `null`) |
| `llamaServer.failed` | 理由(`reason`)、終了コード(`exitCode`) |
| `llamaServer.stop` | きっかけ(`trigger`): `user`(操作) / `providerSwitch`(プロバイダの切り替え) / `projectClose`(プロジェクトを閉じた) / `modelSwitch`(モデルの切り替え) |
| `llamaServer.exited` | 終了コード(`exitCode`) |

- `llamaServer.start` は、起動の直前の一覧の読み直しを通って、起動の command を呼ぶときに出す(取りやめた起動では出さない)。
- 本文・プロンプト・出力の末尾は入れない。
- 動作ログ(本書「ログ」)には書かない。`llama-server` の出力も、どこにも書かない。

### 根拠(2026-11-12 の実測)

RTX 5090(32 GB)の Windows PC で、`llama-server`(ビルド `b1-fdf5818`)と `gemma-4-31B-it` の gguf を使って確かめた。

**text-generation-webui が起動した `llama-server` に直接つなぐ**(Q5_K_M):

- `/v1/completions` のストリーミングは、OpenAI 互換アダプタの SSE の解釈がそのまま通る。`gemma4-think` の思考の開始 `<|channel>` と終わり `<channel|>` は、それぞれ単独のチャンクで文字列として届くので、思考の分離も今の設定のまま使える。
- 最後のチャンクは `"text": ""` と `finish_reason` を持つ。「終了理由を `text` なしで送るサーバー」の制約(本書「思考ブロックの分離」の既知の制約)にはかからず、上限到達を判定できる。
- `POST /tokenize` は、`<|turn>` `<|channel>` `<channel|>` をそれぞれ 1 トークンとして返す。
- `GET /props` で、`default_generation_settings.n_ctx` を読める。

**Sumire と同じ形で起動する**(Q3_K_M、約 15.3 GB。`--fit` は指定しなければ既定の `on`):

| 起動の形 | 準備完了まで | `/props` の `n_ctx` | GPU メモリ | 生成速度 |
| --- | --- | --- | --- | --- |
| `--ctx-size 131072`(`--fit` 既定) | 初回 約 33 秒、2 回目 約 6 秒 | 131072 | 27.7 GB | 65.6 tok/s |
| `--ctx-size 262144`(`--fit` 既定) | 約 12 秒 | 262144 | 29.3 GB | 11.2 tok/s |
| `--ctx-size 262144 --fit off` | 約 8 秒 | 262144 | 31.9 GB | 24.7 tok/s |

- 読み込み中の `/health` は、起動直後は接続を拒否し、すぐに HTTP 503 を返すようになり、読み込みが終わると 200 になる。
- 明示した `--ctx-size` は、収まらない値でもそのまま確保された。`--fit` が調整するのは、指定していない引数(GPU に載せる層の数)のほうだった。
- 存在しないモデルのパスを渡すと、約 0.3 秒で終了コード 1 で終わり、原因は標準エラーの末尾に出る。
- プロセスを強制終了すると、2 秒以内に GPU メモリが起動前の値に戻った。
- `llama-server.exe` は子プロセスを作らず、1 つのプロセスで動く。

コンテキスト長を自動に任せない根拠は、2026-11-01 の経緯にもある。作者の環境でコンテキスト長を自動に任せると 168,960 になり、GPU メモリからあふれて約 1 tok/s まで遅くなった。

詳細は、`llama-server-provider` spec の作業記録(公開しているリポジトリには含めていない)にある。

### 採らなかった案

| 案 | 採らない理由 | 再検討の条件 |
|---|---|---|
| text-generation-webui 専用プロバイダ(text-generation-webui の `/v1/internal/model/load` を呼んで、Sumire からモデルを切り替える) | 実装は小さいが、text-generation-webui 固有の API に依存する。新しいモデルや llama.cpp の更新を取り込む時機を Sumire の側で選べない点が、そのまま残る | text-generation-webui の画面と併用したい理由ができたとき |
| llama.cpp のプロセス内組み込み(Rust から直接呼ぶ) | 推論が落ちると、エディタと未保存の原稿を巻き込む。CUDA ビルドと llama.cpp への追従を Sumire が抱える。`vision.md` の「推論は独立プロセス」に反する | `vision.md` の設計哲学「推論は独立プロセス」を見直すときに限る |
| 準備完了を待ってからの自動の生成 | きっかけの要求では生成せず、準備ができたらトーストで知らせて、書き手が要求し直す形にした(作者と合意、2026-11-12)。読み込みには数十秒かかることがある | 最初の要求を出し直す手間が負担になったとき |
| プロジェクトを開いたときの先読み | 読むだけ・直すだけの日にも GPU を使うことになる。起動は、最初の提案要求のときにする(作者と合意、2026-11-12) | 最初の要求を出し直す手間が負担になったとき |
| text-generation-webui と同じ引数一式(`--flash-attn on --fit on --fit-ctx 8192 --fit-target 512 --batch-size 1024 --ubatch-size 1024`)を既定にすること | `--fit-target 512` は GPU メモリの空きを 512 MiB しか残さず、あふれる原因になっていた。引数名はビルドによって変わりうる。固定で渡す引数は最小限にし、ほかは書き手が追加の起動引数に書く | `llama-server` の既定のままでは性能が出ず、どの環境でも要る引数があると分かったとき |
| ルーターの形(`--models-dir` で、モデルの読み込みを `llama-server` に任せる) | モデルごとにコンテキスト長が違うので、モデルごとの引数を渡すためのプリセットのファイルを Sumire が書き出すことになる。比較的新しい機能で、ビルドによる差が大きい。起動し直しは、どのビルドでも同じに動く。読み込みの時間はどちらの形でもかかる | ルーターの形がビルドの間で安定し、モデルごとのコンテキスト長をプリセットのファイルなしで渡せるようになったとき |
| 固定のポート(設定で変えられる) | text-generation-webui やほかの `llama-server` と衝突しうる。書き手に設定させることになる。フロントは Rust から届く状態でポートを知るので、固定である必要が無い | 空きポートを選んでから `llama-server` が待ち受けるまでの間のポートの取り合いが、実際に起きると分かったとき |
| 異常終了後の自動の再起動 | 終了したことをトーストで知らせ、次の要求で読み込み直す(止まっているときと同じ動線)ので、自動で起動し直さなくても書き手は続けられる | 準備完了のあとの終了が多く、要求し直しが負担になったとき |
| コンテキスト長の自動の決定(GPU メモリからの逆算など) | 自動に任せると大きくなりすぎ、GPU メモリからあふれて極端に遅くなった(2026-11-01)。収まらない値は失敗ではなく速度の低下として現れるので、読み込めたかどうかでは値の良し悪しが分からない。収まる値は量子化ごとに違い、書き手が決める | GPU メモリに収まるコンテキスト長を、読み込む前に見積もれる手段ができたとき |

- 読み込みの時間切れ、設定を変えたときの自動の起動し直し、モデルごとの起動引数、Sumire が起動していない `llama-server` の検出・再利用も持たない。
- 汎用のモデル管理をしないことと、`llama-server` を同梱しないことは `roadmap.md`「採らない方針」。

### `sumire.json`

プロジェクトメタ情報・AI 設定・章グループ定義。

```json
{
  "schemaVersion": "1.0",
  "title": "作品タイトル",
  "author": "著者名",
  "created": "2026-04-28T15:00:00+09:00",
  "ai": {
    "provider": "openai-compatible",
    "endpoint": "http://127.0.0.1:5000/v1",
    "model": "japanese-stablelm-instruct-alpha-7b-v2",
    "parameters": {
      "temperature": 0.8,
      "topP": 0.9,
      "maxTokens": 200
    },
    "candidateCount": 1,
    "systemPrompt": null,
    "settingsTokenBudget": 500,
    "contextWindow": 2048
  },
  "snapshots": {
    "maxKeep": 10
  },
  "chapterGroups": [
    {
      "name": "第一部:出会い編",
      "chapters": ["001-prologue.md", "002-encounter.md"]
    }
  ]
}
```

`systemPrompt: null` の場合はアプリ内蔵の既定プロンプトを使う。文字列を入れれば上書き。

**思考の分離の設定(`thinking`)**: プロバイダごとの AI 接続設定(`aiConfig.providers.<id>`)に、思考ブロックの分離の設定を持てる(規則は本書「思考ブロックの分離」)。`systemPrompt` と同じ階層に置き、`parameters` の中には置かない。`parameters.extras` はリクエスト本文に展開されるので、そこに置くと推論サーバーに送られてしまう。`thinking` は推論サーバーへのリクエストに含めない。

```json
"openai-compatible": {
  "endpoint": "http://127.0.0.1:5000/v1",
  "model": "qwen-finetune-Q4_K_M.gguf",
  "parameters": { "temperature": 0.8, "topP": 0.9, "maxTokens": 1000 },
  "systemPrompt": null,
  "thinking": {
    "enabled": true,
    "tags": [
      { "open": "<think>", "close": "</think>" },
      { "open": "<thinking>", "close": "</thinking>" }
    ]
  }
}
```

- `enabled`: `false` なら分離しない(タグも含めて本文として扱い、導入前と同じ挙動になる)。省略は有効として扱う。
- `tags`: 開始タグと終了タグの組の並び。複数並べられる。
- `thinking` が無ければ、有効・`<think>` / `</think>` の 1 組として動く。
- 開始タグか終了タグが空文字の組は無視する。有効な組が 1 つも無ければ、`<think>` / `</think>` の 1 組として動く。
- 型の合わない部分(真偽値でない `enabled`、配列でない `tags`、`open` か `close` が文字列でない組)は、読み込み時にその部分だけ捨てる。設定の誤りでトーストは出さない。
- 既定値 `{ "enabled": true, "tags": [{ "open": "<think>", "close": "</think>" }] }` は、新規プロジェクトの両プロバイダのセクションにだけ書く。既存プロジェクトの `sumire.json` に `thinking` が無ければ、保存しても書き足さない(読み込みで既定値を埋めない)。書かれていれば、AI 設定画面で他の項目を保存しても失わない。
- 例外として、AI 設定画面のプロンプトテンプレートの欄で `gemma4-think` を選んだときは、Gemma 4 の組が無ければ Sumire が `tags` に書き足す(本書「プロンプトテンプレート」の `gemma4-think` の項)。`thinking` が無いプロジェクトでは、このとき `tags` だけを持つ `thinking` が書かれる。
- 思考の分離の設定の全体(有効・無効、タグの組の編集)は AI 設定画面には出さない。変えるときは `sumire.json` を直接編集する。
- `schemaVersion` は上げない。省略できるフィールドの追加なので、古い Sumire でも読める(古い Sumire で保存すると `thinking` は消えるが、既定値で動く)。

**プロンプトテンプレートの指定(`template`)**: ローカルの Completion のプロバイダの AI 接続設定(`aiConfig.providers.openai-compatible` と `aiConfig.providers["llama-server"]`)に、プロンプトテンプレートの指定を持てる(規則と内蔵プリセットは本書「プロンプトテンプレート」)。`systemPrompt` や `thinking` と同じ階層に置き、`parameters` の中には置かない(`parameters.extras` はリクエスト本文に展開され、推論サーバーに送られてしまうため)。`template` は推論サーバーへのリクエストの項目として送らない。送るのは、テンプレートで包んだ結果の `prompt` だけ。

```json
"openai-compatible": {
  "endpoint": "http://127.0.0.1:5000/v1",
  "model": "gemma-4-31B-it-Q4_0.gguf",
  "systemPrompt": null,
  "template": { "preset": "gemma4" }
}
```

自由記述は `custom` に書く。文字列 1 つでも、行の配列でもよい。配列は改行(`\n`)でつないで 1 本のテンプレートにする。次の例は `gemma4` と同じ中身になる。

```json
"template": {
  "custom": [
    "<|turn>system",
    "{{system}}<turn|>",
    "<|turn>user",
    "{{settings}}<turn|>",
    "<|turn>model",
    "<|channel>thought",
    "<channel|>{{body}}"
  ]
}
```

`gemma4-think` を使い、思考を本文と分けるときは、`thinking.tags` に Gemma 4 の組が要る(既定の `<think>` の組も残す例)。AI 設定画面で `gemma4-think` を選ぶと、Sumire がこの形に書き足す。`sumire.json` を直接編集して指定するときは、書き手が書き足す:

```json
"template": { "preset": "gemma4-think" },
"thinking": {
  "enabled": true,
  "tags": [
    { "open": "<think>", "close": "</think>" },
    { "open": "<|channel>", "close": "<channel|>" }
  ]
}
```

- `{ "preset": 名前 }` か `{ "custom": 文字列または文字列の配列 }` の、どちらか一方だけを書く。両方書く・どちらも書かないと、読めない指定になる。ほかのキーは無視する。
- `template` が無い(または `null`)なら、テンプレートを使わず、導入前と同じ素の連結で送る。
- 既定値で埋めない。新規プロジェクトの `sumire.json` にも書かない。既存プロジェクトに `template` が無ければ、保存しても書き足さない。
- 読み込み時に型を検査しない。読めない値も書かれたまま持ち、AI 設定画面で他の項目を保存しても失わない(書き戻す)。不備は提案要求のたびに解決して判定し、トーストで伝えて生成しない(本書「プロンプトテンプレート」の不備の扱い)。読み込み時にはトーストを出さない。
- AI 設定画面の「プロンプトテンプレート」の欄で、内蔵プリセットと「指定なし」を選べる(2026-11-16、`template-settings-ui` spec)。プリセットを選ぶと `{ "preset": 名前 }` を書き、「指定なし」を選ぶと `template` のキーを消す。自由記述と読めない指定は、画面では「自由記述」「読めない指定」と示すだけで、中身は `sumire.json` で直す。画面で選び直すと置き換わるので、その前に確認を取る。
- OpenAI プロバイダ(`aiConfig.providers.openai`)に書いても使わない。画面にも欄を出さない。
- `schemaVersion` は上げない。省略できるフィールドの追加なので、古い Sumire でも読める(古い Sumire で保存すると `template` は消えるが、素の連結で動く)。
- `sumire.json` を読むのはプロジェクトを開いたときだけ。開いたまま `sumire.json` の `template` を直接書き換えても、開き直すまで前の指定で送られる(`thinking` も同じ)。直接編集はプロジェクトを閉じてから行う。AI 設定画面で選んだ指定は、保存と同時に開いているプロジェクトにも入るので、開き直さなくても次の提案から効く。

**挿し絵の情景文の設定(`illustration`)**: ローカルの Completion のプロバイダの AI 接続設定(`aiConfig.providers.openai-compatible` と `aiConfig.providers["llama-server"]`)に、挿し絵の情景文(本書「挿し絵の情景文」)のための設定を持てる。`template` や `thinking` と同じ階層に置き、`parameters` の中には置かない(`parameters.extras` はリクエスト本文に展開され、推論サーバーに送られてしまうため)。`illustration` は推論サーバーへのリクエストの項目として送らない。

```json
"openai-compatible": {
  "endpoint": "http://127.0.0.1:5000/v1",
  "model": "gemma-4-31B-it-Q4_0.gguf",
  "contextWindow": 16384,
  "template": { "preset": "gemma4" },
  "thinking": {
    "enabled": true,
    "tags": [
      { "open": "<think>", "close": "</think>" },
      { "open": "<|channel>", "close": "<channel|>" }
    ]
  },
  "illustration": {
    "template": { "preset": "gemma4-think" },
    "temperature": 0.7,
    "maxTokens": 4096,
    "timeoutMs": 180000,
    "instruction": "(省略すると内蔵の指示文。文字列か文字列の配列)"
  }
}
```

この例は、続き生成は思考なしの `gemma4`、挿し絵は思考ありの `gemma4-think` で使い分ける形。`contextWindow` の値は例で、推論サーバーで読み込んだモデルのコンテキスト長に合わせる。`llama-server` のセクションでは、`endpoint`・`model`・`contextWindow` を書かない(下の「`llama-server` のセクション」)。

| キー | 必須 | 既定値 | 意味 |
| --- | --- | --- | --- |
| `template` | 必須 | なし | 挿し絵用のテンプレート。書き方は `template` と同じ(`{ "preset": 名前 }` か `{ "custom": 文字列または文字列の配列 }`)。プリセットの名前は同じ 4 つだが、中身は挿し絵用(本書「挿し絵の情景文」の「挿し絵用のプリセット」) |
| `temperature` | 省略可 | `0.7` | 挿し絵用の温度 |
| `maxTokens` | 省略可 | `4096` | 挿し絵用の最大トークン。思考に使ったトークンも含む。思考と情景文の両方が収まる量を既定値にしている |
| `timeoutMs` | 省略可 | `180000` | 挿し絵用のタイムアウト(ミリ秒)。リクエスト全体の時間で、思考の時間も含む |
| `instruction` | 省略可 | 内蔵の指示文 | 指示文の差し替え。文字列か、文字列の配列(改行 `\n` でつなぐ)。続き生成の `systemPrompt` とは別 |

- 必須は `template` だけ。`illustration` が無い、または `template` が無い(`null` を含む)と、情景文を生成せず、`illustration.template` を書くよう促すトーストを出す。素の連結に黙って戻さない(本書「挿し絵の情景文」の「採らなかった実装の案」)。
- `illustration` がオブジェクトでない(配列を含む)と、読めない設定としてトーストを出す。`template` の不備は、続き生成のテンプレートの不備と同じ 4 種で判定し、文言の頭に「挿し絵用の」を付けて伝える。
- `temperature` は有限の数なら採る。`maxTokens` / `timeoutMs` は有限の正の数なら採る。それ以外の値は、トーストを出さずに既定値にする。
- `instruction` は、前後の空白を除いて空なら内蔵の指示文を使う。文字列でも文字列の配列でもない値も、内蔵の指示文になる。
- ほかのキーは無視する。`topP` と `extras` は持たず、続き生成の `parameters` の値を使う。接続先・モデル・`contextWindow`・`settingsTokenBudget`・`thinking` も続き生成と共通。
- **`contextWindow` に注意**: 予算配分(本書「挿し絵の情景文」の「予算配分」)は `contextWindow` から挿し絵用の `maxTokens` を差し引く。`contextWindow` が既定の 2048 のままだと、既定の `maxTokens`(4096)を引いた残りが負になり、毎回「場面がコンテキストに収まりません」になる。`contextWindow` を推論サーバーで読み込んだモデルのコンテキスト長に合わせるか、挿し絵用の `maxTokens` を下げる。`contextWindow` は続き生成と共通なので、上げると続き生成で送る直前の本文も長くなる。`llama-server` プロバイダでは、`contextWindow` の代わりに、いま使うモデルに決めてあるコンテキスト長が使われる。
- 解決の口は `domain/illustration/illustrationConfig.ts` の `resolveIllustrationConfig` に限る。解決は `Alt+I` のたびに行い、読み込み時にはトーストを出さない。
- 読み込み時に型を検査しない。読めない値も書かれたまま持ち、AI 設定画面で他の項目を保存しても失わない(書き戻す)。
- 既定値で埋めない。新規プロジェクトの `sumire.json` にも書かない。既存プロジェクトに `illustration` が無ければ、保存しても書き足さない。
- AI 設定画面には出さない。変えるときは `sumire.json` を直接編集する。続き提案のテンプレート(`template`)は 2026-11-16 から画面で選べるようになったが、挿し絵用のテンプレート(`illustration.template`)を含む `illustration` は対象にしていない(`roadmap.md`「今回採らなかったもの」)。
- OpenAI プロバイダ(`aiConfig.providers.openai`)に書いても使わない(情景文は、ローカルの Completion のプロバイダでだけ使える)。保存しても消さない。
- `schemaVersion` は上げない。省略できるフィールドの追加なので、古い Sumire でも読める(古い Sumire で保存すると `illustration` は消える)。
- `sumire.json` を直接編集したら、プロジェクトを開き直す。開いたまま `illustration` を書き換えても、開き直すまで前の設定で生成する(`sumire.json` を直接編集した `template` / `thinking` と同じ)。

**`llama-server` のセクション(`aiConfig.providers["llama-server"]`)**: `llama-server` プロバイダ(本書「llama-server プロバイダ」)の、作品ごとの設定を持つ(2026-11-12、`llama-server-provider` spec)。形はほかのプロバイダのセクションと同じ。

```json
"llama-server": {
  "endpoint": "",
  "model": "",
  "parameters": { "temperature": 0.8, "topP": 0.9, "maxTokens": 200 },
  "systemPrompt": null,
  "settingsTokenBudget": 500,
  "template": { "preset": "gemma4" },
  "thinking": {
    "enabled": true,
    "tags": [{ "open": "<think>", "close": "</think>" }]
  }
}
```

- 使うのは `parameters`、`systemPrompt`、`timeoutMs`、`settingsTokenBudget`、`thinking`、`template`、`illustration`。規則は OpenAI 互換プロバイダのセクションと同じ。
- `endpoint` と `model` は空文字にする。`contextWindow` は書かない(既定のセクションにも持たせない)。書かれていても使わない。接続先・モデル・コンテキスト長は、起動した `llama-server` の状態と、アプリ側の設定(`preferences.json`)から決まる。
- `llama-server` の実行ファイルのパス、モデルのフォルダ、モデルごとのコンテキスト長、いま使うモデル、追加の起動引数は、ここには書かない(本書「llama-server プロバイダ」の「設定の置き場所」)。
- 既存のプロジェクトにこのセクションが無ければ、読み込み時に既定値で補う。`activeProvider` は変えない。次に AI 設定を保存したときに書き足される。新規プロジェクトの `sumire.json` には、最初からこのセクションがある。
- `schemaVersion` は上げない。古い Sumire は、知らないプロバイダのキーを保存時に落とし、`activeProvider` が `llama-server` なら OpenAI 互換に戻す(既存の挙動)。

### 章ファイル(`chapters/*.md`)

YAML フロントマター + 本文。

```markdown
---
title: プロローグ
created: 2026-04-28T15:30:00+09:00
updated: 2026-04-28T16:00:00+09:00
---

(本文)
```

- 文字数カウントはフロントマターを除外して計算する。
- 投稿時のサブタイトルは `title` を使う。

### 設定ファイル(`characters/*.md` 等)

YAML フロントマター + Markdown 本文。

```markdown
---
title: アリス
includeInContext: false
---

(キャラの説明)
```

- `includeInContext: true` のファイルは生成リクエスト時にコンテキストへ自動挿入される。
- ファイルを移動・削除すると追従的に挿入対象から外れる(集中管理しないため)。

### `memo.md`

プレーンな Markdown ファイル。フロントマターなし。
ユーザーが提案候補を流し込んだり、自由メモを書いたりする領域。

メモへの転記エントリのフォーマット(MVP 暫定):

```
***
YYYY-MM-DD HH:mm
<本文>
```

区切りに `***` を使うのは、`---` だと直前行を Markdown の setext 見出しのアンダーラインと解釈されて装飾が崩れるため。フォーマットは `formatMemoEntry` 1 箇所に閉じ込め、将来差し替え可能にしてある。

### スナップショット(`history/*.json`)

`Ctrl+S` 押下時にプロジェクト全体の状態を一括保存する。

```json
{
  "snapshotVersion": "1.0",
  "timestamp": "2026-04-28T15:30:00+09:00",
  "files": {
    "sumire.json": "...",
    "chapters/001-prologue.md": "...",
    "characters/alice.md": "...",
    "memo.md": "..."
  }
}
```

- 全ファイル内容を埋め込む(差分ではない)
- 既定保持件数: 10。`sumire.json` の `snapshots.maxKeep` で変更可
- 古いものから自動削除

## ファイル管理の方針

### 削除は `.trash/` 移動

章・設定ファイルの削除は OS のゴミ箱には送らず、プロジェクト内の `<folder>/.trash/` に移動する。プロジェクトをそのまま別マシンに持ち運んでも復元可能とするため。

### slug 化のルール

ファイル名生成時のタイトル → slug 変換規則:

- 日本語タイトルはそのまま使う(URL 安全性は問わないため)
- ファイル名禁止文字(`\ / : * ? " < > |` 等)は半角スペースに置換、または除去する
- 重複時は末尾に `-2`, `-3` を自動付与する

### 章ファイルの連番採番ポリシー

- 章を削除しても連番は詰めない(欠番のまま残す)
- 再採番すると過去スナップショットとの参照が崩れるため
- 「並び替え」(ドラッグ&ドロップ)時のみ連番をリナンバリングする
- 連番幅は 3 桁固定(`001` 〜 `999`)。1000 話超は将来検討

## 編集中の保存(オートセーブ)

スナップショットとは別に、現在編集中のファイル内容をディスクに反映する自動保存層を持つ。

### 三層の保存モデル

| 層 | 何を保存 | いつ | 目的 |
|---|---|---|---|
| **未保存バッファ** | エディタ内のメモリ状態 | 編集中常時 | UI のレスポンシブネス |
| **オートセーブ** | `chapters/*.md` 等の現在ファイル | 数秒おき(無編集時) | クラッシュ耐性 |
| **スナップショット** | `history/*.json` | `Ctrl+S` 押下時 | 復元ポイント |

オートセーブは「ファイルを上書き」する。現在の状態を常にディスクに反映する。
スナップショットは「履歴を増やす」。任意の時点に戻れる。

### オートセーブの間隔

- 無編集状態が **2 秒続いた**らディスクへ書き込む(デバウンス)
- 編集中(キー入力中)は書き込まない

## エディタ実装の採用技術

### 採用フレームワーク

- **エディタ本体**: CodeMirror 6
  - インライン提案(ゴーストテキスト)は Decoration API で実装
  - ルビ表示(`|漢字《かんじ》` → 装飾)も Decoration API
- **UI コンポーネント**: 自作の Tailwind ベース primitive(`src/components/ui/`)。仕様策定当初は shadcn/ui 採用を想定していたが、依存削減のため自作に切り替えた経緯がある
- **状態管理**: Zustand
- **ビルド**: Vite(Tauri テンプレート標準)

### CodeMirror 6 の主要拡張

- `@codemirror/state`, `@codemirror/view`(コア)
- 自前の `ghostTextExtension`(提案表示用)
- 自前の `rubyDecorationExtension`(ルビ装飾)
- 自前の `wordCountExtension`(文字数カウント)

### IME(変換中入力)の扱い

提案ゴースト表示中に IME 変換が始まっても、ゴーストはキャンセルする。書き手が IME を起動した時点で「自分で続きを書こうとしている」意思表示と解釈するため、変換確定を待たずに消す方が一貫する。

実装上は `compositionstart` / `compositionend` の特別扱いを行わず、通常の `docChanged` キャンセルに任せる。

### 文字数カウントの単位

- 単位: 文字数
- 既定: 「改行除く・空白含む」(Web 小説サイトの慣例に合わせる)
- スコープ切替: 「現在の章」と「プロジェクト全体」の 2 種類
- 章ファイル本文の計測時はフロントマターを除外する
- 原稿用紙換算・単語数は実装容易ならば追加する程度の位置づけ

## エラーハンドリング方針

- **ユーザー操作起因のエラー**: トーストで通知。本文編集は継続可能。
- **ファイル I/O 失敗**: ダイアログ表示。可能なら再試行を提案。
- **推論サーバー接続失敗**: 提案要求と情景文の生成(`Alt+I`)のたびにトースト。常時監視はしない。
- **`llama-server` の状態の知らせ**(`llama-server` プロバイダ): 読み込みの開始・準備完了・起動や読み込みの失敗・準備完了のあとの終了を、状態が変わったときにトーストで知らせる。設定が足りなくて起動できないときも、要求のたびにトーストで知らせる。失敗や終了のあとに、自動で再試行・再起動はしない。本文編集は継続可能(文言は `ux.md`「llama-server のトーストの一覧」)。
- **致命的エラー(状態破壊の恐れ)**: モーダルで通知し、強制保存を促す。

## アプリデータディレクトリ

プロジェクトに紐づかないアプリ全体の状態(最近のプロジェクト一覧、アプリ環境設定、動作ログ等)は、各 OS の標準データディレクトリ配下の `Sumire/` に集約する。

| OS | パス |
|---|---|
| Windows | `%LOCALAPPDATA%\Sumire\`(= `~\AppData\Local\Sumire\`) |
| macOS | `~/Library/Application Support/Sumire/` |
| Linux | `~/.local/share/Sumire/` |

配置物:

- `recent.json`: 最近のプロジェクト一覧(最大 10 件)
- `preferences.json`: アプリ側の設定。今は `llama-server` プロバイダの設定(`llamaServer`)だけを持つ(2026-11-12、`llama-server-provider` spec。形は本書「llama-server プロバイダ」の「設定の置き場所」)。ファイルが無ければすべて未設定として動き、最初に保存したときに作る。`llamaServer` 以外のトップレベルのキー(将来のアプリ設定)は、読んだまま書き戻す
- `logs/sumire-YYYY-MM-DD.log`: 動作ログ

旧バージョン(2026-04 系)では `~/.sumire/` 直下に置いていた。`recent.json` のみ初回起動時に新パスへ自動移行する(`recent.rs` の `migrate_legacy_recent`)。他のファイル(将来追加されるもの)は最初から新パスのみで扱い、移行は recent に閉じる。

## ログ

- アプリの動作ログは `<アプリデータディレクトリ>/logs/sumire-YYYY-MM-DD.log` に出力する。

- 詳細レベルは `sumire.json` の `logging.level` で制御(MVP は `info` 固定でも可)。
