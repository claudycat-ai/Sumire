# Sumire — 機能スコープ / 拡張ロードマップ

本書は **将来やる/やらない** の判断軸を恒久的に残す文書。すでに動いている機能の磨き込みは `polish-backlog.md`、すでに撤退/採用しないと決めた小さな項目はそちらの「バックログに入れない方針のもの」を参照。

本書が扱うのは「**今は実装していないが、将来取り組む可能性がある拡張テーマ**」と「**MVP では意図的に切ったが、将来必要になれば再検討するテーマ**」。

## 同ジャンルのツールとの関係

Sumire の近くには、性格の違う 2 種類のツールが先行している。どちらにも Sumire より機能が厚い部分があり、Sumire は「狭い軸に特化する」立ち位置で並走する(差別化軸は `vision.md` 参照)。将来のテーマを判断するときの参考として、特徴だけを残す。

- **総合環境型**: ノードグラフでアイデアを広げ、Markdown に変換し、AI の支援で執筆するまでを 1 つにまとめたアウトライナー。ショートカットでの続き生成、ノード間のプロット補完、補完・リライト・翻訳などのコマンド、複数のクラウドプロバイダとローカル AI、画像生成との連携、縦書きプレビュー、EPUB / HTML 出力を備える。
- **Notebook 型**: Completion ベースで、本文を起点に続きを生成する、ローカル LLM のフロントエンド。思想は Sumire に最も近い。起動の手間が小さく、複数の推論サーバーに対応し、キャラ・世界観に相当するメモを持つ。トークンごとの確率を見て、分岐して再生成できる。日本語 Web 小説の連載に合わせた動線(章の管理など)は持たない。

## 拡張ロードマップ(将来取り組む可能性のあるテーマ)

着手判断は「Sumire の差別化軸に沿うか」で行う(`vision.md` 参照)。沿わない機能は採らない。

### 挿絵生成(情景文の生成まで実装済み)

- **状況**: 本文で選んだ場面から、挿し絵のための日本語の情景文を生成し、メモに追記するところまでを実装した(2026-11-05、`illustration-prompt` spec。操作は `ux.md`「挿し絵の情景文」、内部仕様は `architecture.md`「挿し絵の情景文」)。画像生成ツールは呼ばない。書き手は情景文をメモで直し、ComfyUI の日本語→英語のプロンプト変換ワークフローに通して、人物の外見などの手打ちのタグにつなぐ。
- **Sumire が受け持つ範囲**: 書き手の運用で手間がかかっていたのは、本文を読み返して場面の情景(位置関係、視線、光、小道具、構図)を拾い、日本語の文章にまとめるところだった。Sumire はそこだけを受け持つ。外見のタグ、品質の指定、英訳、画像の生成は、書き手と ComfyUI の側に残す。
- **差別化軸との関係**(`vision.md`「Sumire が守るべき軸」):
  - 1「Copilot 風インライン Tab 採用 UX」: 触れない。続き提案のプロンプト・ゴースト・`Tab`・`Shift+Enter`・`Alt+M` は変えない。起動は別のキー(`Alt+I`)で、生成中も止めずに書き続けられる。
  - 2「本文起点の文脈構築」: 起点は本文の選択範囲(無ければカーソルのある行)で、文脈も今の章の本文と「コンテキストに含める」設定だけ。中間表現は作らず、結果はいつものメモに入る。
  - 3「OpenAI 互換 API をプロバイダ抽象に」: ローカルの OpenAI 互換プロバイダで、続き生成と同じ接続先・モデルを使う。挿し絵用に別の接続先は持たない。2026-11-12 からは、Sumire が起動する `llama-server` プロバイダでも使える(`architecture.md`「llama-server プロバイダ」)。
- **やらない判断軸**: 本文起点でなくなったら(=独立した画像生成画面が主動線になったら)採らない。今回も独立した画像生成画面は作らず、書き手はメモで直してコピーする。
- **将来のテーマ**(再検討の前提条件つき):
  - **ComfyUI の直接呼び出し(画像の生成・管理)**: 今は採らない。今の運用では、外見のタグは書き手が手打ちし、英訳は既存の変換ワークフローが受け持っている。Sumire から呼ぶと、ワークフローやタグの組み立てを Sumire の側に持つことになり、生成した画像を見て選ぶ画面も要りうる。再検討の前提条件: 情景文を ComfyUI に手で渡す手間が、情景文を作る手間より目立つようになったとき。その場合も、独立した画像生成画面を主動線にしない形に限る。
  - **クラウド(OpenAI プロバイダ)での生成**: 今は採らない。ローカルの思考ありのモデル(`gemma-4-31B-it` + `gemma4-think`)が文脈から場面を整理することを想定している。クラウドの Chat 経路は system に続き生成の指示を前置きするので、指示に答えさせるにはアダプタ側の見直しが要る。再検討の前提条件: `gemma4-think` で情景文の品質が足りないと分かったとき。
- **この spec で採らなかったもの**:
  - **英訳と、タグ・品質の接頭辞・仕上げタグ・ネガティブプロンプトの生成**: 英訳は既存の ComfyUI の変換ワークフローに任せ、英訳の決まりを Sumire の側に二重に持たない。外見のタグは書き手が手打ちし、絵が意図と違ったときにタグで調整している。そこを AI に任せると、手打ちのタグと食い違う。再検討の前提条件: 書き手が変換ワークフローを使わなくなったとき、または外見のタグを AI に任せたくなったとき。
  - **構造化した情景メモ(人物・場所・光などの欄)と 2 段構成(情景メモ → プロンプト)**: 選択範囲と前後の文脈から情景文を 1 段で作り、場面の整理は思考ありのモデルの思考に任せる。英訳とタグを作らないので、2 段目が要らない。再検討の前提条件: 英訳やタグを Sumire の側で作るようにしたとき、または 1 段の情景文で位置関係や構図の取りこぼしが目立ち、欄を直してから作り直したくなったとき。
  - **生成のたびの追加の指示**(「横長の構図で」など): 入力欄を出すと、`Alt+I` 一発の動線に画面が挟まる。構図の注文は、追記された情景文をメモで直すか、`sumire.json` の挿し絵用の指示文を差し替えれば足りる。再検討の前提条件: 場面ごとに違う構図の注文を毎回メモで直すようになり、指示文の差し替えでは賄えないと分かったとき。2026-11-05 の実機確認では、構図の視点(俯瞰、背中越しなど)は本文に書かれていなくてもモデルが選んで書いた。書き手の判断で、今のまま運用してメモで直す。
  - **前の章を読むこと**: 続き生成と同じく、今の章ファイルの中だけを読む(`architecture.md`「章境界の扱い」)。長期の文脈は設定ファイルで補う。再検討の前提条件: 場面の理解に前の章が要る場面が多く、設定ファイルで補いきれないと分かったとき。
  - **挿し絵の設定を AI 設定画面に出すこと**: 思考の分離の設定(`thinking`)と同じく、`sumire.json` の直接編集だけにする。頻繁に変える設定ではないため。続き提案のテンプレート(`template`)は、2026-11-16 に画面から選べる形に改めたが(下の「プロンプトテンプレートの画面での選択」)、挿し絵用はその対象にしていない。再検討の前提条件: 挿し絵の設定を頻繁に切り替えるようになり、`sumire.json` の直接編集と開き直しが負担になったとき。
  - **失敗したときの自動の再試行**: 失敗はトーストで理由を伝え、書き手が `Alt+I` を押し直せばやり直せる。思考ありの生成は数十秒かかる想定なので、黙って繰り返すと待ち時間が読めなくなる。再検討の前提条件: 一時的な接続の失敗が多く、押し直しが負担になったとき。

### プロンプトテンプレートの画面での選択(実装済み)

- **状況**: 続き提案のプロンプトテンプレート(`architecture.md`「プロンプトテンプレート」)を、AI 設定画面で内蔵プリセットと「指定なし」から選べるようにした(2026-11-16、`template-settings-ui` spec。操作は `ux.md`「AI 接続設定 UI」の「プロンプトテンプレートの欄」)。対象はローカルの Completion のプロバイダ(OpenAI 互換と `llama-server`)。
- **経緯**: `prompt-template` spec では、テンプレートを画面に出さず、`sumire.json` の直接編集だけで指定していた。公開後、初めて使う書き手には設定の存在が分からず、指示に答える形で学習されたモデルで出力が崩れる、いちばんの障害になっていたので改めた。
- **差別化軸との関係**: 続き提案の動線(ゴースト・`Tab`)と、プロンプトに自動で構造を足さない方針は変えない。テンプレートは書き手が選んだときだけ使い、新規プロジェクトは今までどおり指定なしで始まる。
- **この spec で採らなかったもの**:
  - **モデルの名前からの候補の提示・自動の選択**: 選んだモデルのファイル名から、合いそうなプリセットを示す案。名前の付け方はモデルの配布元ごとに違い、外れたときに書き手を迷わせる。まず選択欄だけを使ってみて判断する。再検討の前提条件: 選択欄を使っても、モデルに合うプリセットが分からずに迷う書き手が多いと分かったとき。
  - **挿し絵用のテンプレート(`illustration.template`)を画面に出すこと**: 挿し絵の設定は、ほかの項目(温度、最大トークン、タイムアウト、指示文)とまとめて `sumire.json` で持つ。テンプレートだけを画面に出すと、画面と直接編集の境目が分かりにくくなる。再検討の前提条件: 挿し絵の設定を頻繁に切り替えるようになり、`sumire.json` の直接編集と開き直しが負担になったとき(上の「挿絵生成」の同じ項と合わせて判断する)。なお、新規プロジェクトのままでは `illustration.template` が無く `Alt+I` が使えなかったので、2026-11-17 に、`illustration.template` が無いときは続き提案のプリセットと同じ名前の挿し絵用のプリセットを使う形にした(`architecture.md`「挿し絵用のプリセット」)。画面に欄は足していない。
  - **自由記述のテンプレートを画面で書く・直すこと**: プリセットに無いモデルのための口で、書く書き手は限られる。画面では「自由記述」と示し、選び直すときに置き換わることを確認するだけにした。再検討の前提条件: 自由記述を書く書き手が増え、`sumire.json` を閉じて直す手間が負担になったとき。
  - **Max Tokens やタイムアウトを自動で書き換えること**: 思考ありのプリセットを選んだときも、案内を出すだけにした。値は書き手が決める。再検討の前提条件: 案内を読んでも上げ忘れて、提案が空になることが続くと分かったとき。

### クラウドプロバイダの拡充(Claude / Gemini / Mistral / Cohere 等)

- **状況**: MVP では OpenAI 互換 1 系統のみ実装。
- **取り組む場合の方針**: OpenAI 互換でないものはアダプタで吸収する設計方針は既存のまま。Chat 系しか提供しないプロバイダの場合は、アダプタ内部で chat メッセージへの変換を行い、`AIProvider.generate` の契約(=テキストの続きを返す)を守る(詳細は `architecture.md` の「プロバイダ抽象」節)。
- **API キーを使う接続先の追加**: 今は、キーを付ける相手を `https://api.openai.com` に固定している(`architecture.md`「IPC 境界」)。OpenAI 互換の API を持つほかのクラウドにキーつきでつなぐことはできない。接続先は作品ごとの設定なので、自由にすると、受け取ったプロジェクトを開いただけでキーが第三者に渡りうるため。再検討の前提条件: ほかのクラウドを使いたい具体的な要望が出たとき。その場合は、接続先とキーの組を PC ごとの設定(アプリ側)に持ち、書き手がその PC で認めた接続先にだけキーを付ける形にする。
- **取り組み手順**: `polish-backlog.md` の「AI プロバイダ設定をプロバイダごとセクション化」「メイン/サブモデル指定」の磨き込み項目とセットで進める。

## MVP では意図的に切ったテーマ

将来必要になれば再検討するが、MVP 期では複雑度に対して投資対効果が悪いと判断したもの。

- **複数 AI プロバイダの同時切り替え UI**: MVP は設定ファイルでの切替で十分とした。同時切替の必要が出た時点で UI 化を検討。
- **縦書きプレビュー / 禅モード / EPUB・HTML 出力**: 執筆環境としての完成度を上げる要素ではあるが、Sumire の主動線(本文連載執筆)には必須でない。

## 採らない方針

差別化軸を歪めるため意図的に取らないもの(本ファイルが正、`polish-backlog.md` から参照される):

- **AI へのキャラクター付与**(AI に名前や人格を持たせること): Sumire の AI は黒子に徹する。書き手と本文の間に AI 人格が割り込まない。
- **ノードグラフ式アウトライナー**: 本文起点の軸を崩す。
- **チャット型 UI を主動線にする**: Sumire の主動線はインラインゴーストテキスト + Tab 採用。チャットは補助に留める(現状チャット UI 自体無いが、追加するとしても主動線昇格はしない)。
- **トークン確率分岐 UI**(トークンごとの top-N 確率を表示し、クリックで分岐して再生成する機能): Notebook 型のツールでは強力な機能だが、Sumire では採らない。理由は (1) 主動線「インライン Tab で一筆書きに採用」とは思想が衝突する(分岐は書き手を本文の流れから引き剥がす)、(2) 確率分岐は、候補を見比べながら出力を探る使い方に向いた機能で、Sumire の「連載日次ワークフロー」とは使う場面が違う。再検討の前提条件: 書き手から「Tab で採用する一手前に候補を見比べたい」という具体的な要望が複数出てきた場合に限り、分岐 UI ではなく**インライン候補のサイクル切替**(現実装の延長)で対応するか再考する。
- **汎用のモデル管理**(モデルのダウンロード、一覧の整理・絞り込み・並べ替え、モデルごとの生成パラメータやテンプレートの切り替えなどの細かな調整): `llama-server` プロバイダ(2026-11-12、`llama-server-provider` spec。`architecture.md`「llama-server プロバイダ」)は Sumire が推論サーバーを起動するが、受け持つのは、書き手が指したフォルダの gguf を並べ、選ばれたモデルを決めてあるコンテキスト長で起動して止めるところまで。Sumire は執筆の道具で、モデルを管理する道具にはしない。対象も、作者が使う gemma4 の gguf で足りる。生成パラメータ・テンプレート・思考の分離は、今までどおり作品ごと(`sumire.json`)に持つ。再検討の前提条件: 使うモデルの種類が増え、モデルごとにテンプレートや生成パラメータを手で書き換える手間が、量子化の切り替えの手間より目立つようになったとき。その場合も、ダウンロードと一覧の整理は外のツールに任せる。
- **`llama-server` のバイナリの同梱**(ダウンロード・更新を含む): 同梱しない。書き手が自分の GPU に合ったビルドを用意し、パスを設定で指す(当面は text-generation-webui が入れたバイナリを指せる)。同梱すると、CUDA などのビルドの違いと llama.cpp の更新への追従を Sumire が抱えることになる。バイナリを書き手が差し替えられる形にしておけば、Sumire を更新しなくても新しい llama.cpp に追従できる。再検討の前提条件: 配布の範囲が広がり、書き手がバイナリを自分で用意することが使い始めの妨げになると分かったとき(「配布パッケージ・署名・自動更新」と合わせて検討する)。
